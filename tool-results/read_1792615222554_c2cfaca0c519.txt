    54→# 2. MISSION AND CONTEXT
    55→
    56→**Product.** MIZAN (ميزان, "the balance"): continuous HR policy assurance for Emirates Group HR. It replaces sampling with a census. Every HR transaction is checked against every written rule on every run by a deterministic engine whose output is reproducible to the byte. Each exception explains itself in plain English or Arabic, cites the rule and the exact data that broke it, carries a severity, an owner and a corrective action, and waits for a person to decide. Language models never decide anything.

    60→2. Explain each exception in plain language, citing the rule and the data that broke it.
    61→3. Route each exception to the right owner with a severity and a suggested corrective action.
    62→4. Show hotspots, trends and audit readiness.
    63→5. Nice-to-haves, all built: rules written in plain English without code; pattern alerts for risks no rule covers; Arabic and English; employee-experience fairness principles.

    97→## Spec · PRD §5 Product principles
    98→
    99→1. **Census, not sample.** Every transaction × every active rule, every run. Coverage is measured and displayed, never assumed.
   100→2. **The engine decides, the model explains.** Exceptions come from deterministic rules. A model never decides, scores, routes or closes anything.
   101→3. **Traceable or not shown.** Every exception carries the rule ID, rule version, verbatim clause, evidence values and the run manifest.
   102→4. **Unknown is not pass.** Missing or ambiguous data yields "not evaluable" plus a data-quality exception, never a silent pass.
   103→5. **The tool recommends; a person decides.** Every exception needs a human decision. Dismissing a High or Critical exception needs a second person.
   104→6. **Precision is a feature.** A noisy queue is an ignored queue. Rules ship only after backtesting, and a flood guard holds runaway rules.
   105→7. **Explain like a colleague.** Plain language, neutral tone, sentences of 25 words or fewer, the fix on the first screen, in English or Arabic.
   106→8. **Process, not people.** Exceptions describe transactions and controls, not character. No individual risk scores, ever.
   107→9. **Replayable to the byte.** The same inputs, rule pack and configuration produce identical outputs and identical hashes.
   108→10. **Deployable inside the walls.** Runs fully offline in Emirates' environment. AI is optional and local.

   123→# 4. NON-NEGOTIABLES
   124→
   125→1. **The engine decides, the model explains.** `packages/engine` has no model, network, clock or randomness imports, enforced by a dependency-cruiser rule.
   126→2. **Census.** Every transaction × every active rule ends in exactly one outcome: PASS, FAIL, NOT_APPLICABLE or NOT_EVALUABLE. Finalize asserts completeness (FS-02).
   127→3. **Determinism.** The same inputs give byte-identical output and the same output hash: canonical JSON (RFC 8785), SHA-256, stable sorting, integer fils, explicit as-of date.
   128→4. **Never invent a fact.** Missing or ambiguous data gives NOT_EVALUABLE with a DQ code. A default can influence an outcome only with a caveat in the evidence.
   129→5. **Every exception is complete:** rule ID and version, verbatim clause, evidence (field, value, requirement, comparison), severity with rationale, owner with routing rationale, corrective action, caveats, and explanations in English and Arabic.
   130→6. **Identity.** Exception key = SHA-256(tenant ‖ transaction row ID ‖ rule ID ‖ clause ID). Upserts are idempotent and each run appends an observation.
   131→7. **Humans reduce scrutiny; the engine never does.** The engine may only create, reopen, or return an expired accepted risk to triage. Dismiss, accept risk, verify and close are human commands.
   132→8. **Conflict-of-interest guard, two-person rule approval, countersign for High and Critical dismissals.** Enforced in the API and in the database, not only in the UI.
   133→9. **Tamper-evident audit.** Append-only, hash-chained events; hourly verification; a failure enters safe halt.
   134→10. **No writes to any source system.** MIZAN never holds write credentials.
   135→11. **Synthetic data only.** PII scanner on uploads; judge mode refuses untagged datasets.
   136→12. **Fact-lock** on any model text, with canonical template fallback.
   137→13. **Free text is data, never instructions.**
   138→14. **Guards:** flood guard, run-level routing hold and not-evaluable spike guard.
   139→15. **Pattern alerts are advisory:** never exported, never routed as breaches, protected attributes excluded.
   140→16. **One retry helper, explicit timeouts on every call, typed errors, no empty `catch`.**
   141→17. **Idempotency keys on every mutating endpoint; transactional outbox and consumer inbox.**
   142→18. **Caches are never authoritative.** The system is correct with Valkey switched off.
   143→19. **WCAG 2.2 AA, and Arabic right-to-left as a first-class layout.**
   144→20. **Every state is designed:** loading, empty, error, partial, held, stale, offline, no access, and every degraded mode.
   145→21. **Exports validate** against `finding_format.csv`, and the 5 worked examples reproduce exactly.
   146→22. **Configuration is versioned data:** routing, calendars, grade ladder, synonyms, severity rubric, service levels and templates.
   147→23. **Small cells below 5 are suppressed** in analytics.
   148→24. **No personal data** in logs, metrics or traces.
   149→25. **Safety controls are code, not flags.**

   303→# 8. INGESTION AND NORMALISATION
   304→
   305→**Pipeline:** receive (stream to object storage while hashing with SHA-256) → sniff (magic bytes; encoding from BOM, UTF-8 validity, UTF-16 or Windows-1256; delimiter from the first 64 KB) → parse (RFC 4180 streaming parser; limits of 50 MB per file, 1 MB per line, 32 KB per field and 2,000,000 rows) → header mapping (synonym tables, header fingerprint, saved mapping profile) → field normalisation → schema validation → quarantine of invalid rows → dataset record with an issues summary. Identical bytes return the existing dataset.
   306→
   307→**Field normalisers** (each a pure function with unit and property tests):
   308→- Text: NFKC, strip zero-width characters, collapse whitespace, trim; flag confusable characters (DQ-014). Missing tokens (empty, whitespace, N/A, null, -) become missing (DQ-001 where required).
   309→- Digits: Arabic-Indic and Persian digits, the Arabic decimal separator (٫) and thousands separator (٬) become ASCII before any parsing.
   310→- Dates: ISO, day-month-year with `/`, `-` or `.`, two-digit years (pivot 2000), month names in English and Arabic, spreadsheet serials (20,000–80,000). Day-month order is inferred per column from unambiguous values; a fully ambiguous column defaults to day-month with DQ-003; cells contradicting the column's order get DQ-002.
   311→- Timestamps: explicit offsets honoured; no offset means Asia/Dubai (UTC+4, no daylight saving); stored as UTC instants with a precision flag.
   312→- Amounts: strip currency words and symbols; decide the decimal convention per column; parentheses mean negative; scientific notation allowed; convert to integer fils. More than 2 decimals or a value ambiguous under the column convention gives DQ-013. Currency other than AED gives DQ-009, and amounts are never converted without a versioned FX table.
   313→- Identifiers: canonicalise with the tenant pattern from configuration (case, prefix, zero padding); log every mapping; a collision onto a different person gives DQ-014.
   314→- Lists: approvers and documents from `;`, `,`, `|`, JSON arrays or numbered columns (`approver_1` … `approver_n`), keeping order and removing exact repeats with a caveat.
   315→- Vocabularies: transaction types, document types, statuses, departments and locations map through versioned synonym tables; unknown values get DQ-006, DQ-007 or DQ-016 and are suggested to a person, never auto-accepted.
   316→- Booleans: Y, yes, true, 1, نعم and their negatives.
   317→- Free text: stored verbatim as quoted data, scanned for instruction-like text (DQ-017) and never read by the engine.
   318→
   319→**Mapping review.** Unknown columns, low-confidence header matches and new vocabulary values appear on a mapping screen. Confirmed choices are saved as a versioned mapping profile that is pinned in the run manifest. Every edge case in sections 34.A and 34.B must pass.

   375→**Condition grammar** for `scope.where` and conditional parameters: `{ all: [...] }`, `{ any: [...] }`, `{ not: {...} }`, `{ fact, op, value }` with ops `eq, ne, gt, gte, lt, lte, in, nin, between, exists, missing`. No regular expressions and no code in specs. Every `fact` must exist in the fact catalogue (section 7 derived facts), otherwise compilation fails with `MZ-RULE-422`.
   376→
   377→**Family semantics** (each family is one module in `packages/engine/families/` with its own tests):
   378→- `approval_limit` { thresholdFils, comparator gt|gte, minApproverGrade, quantifier any|all, allowDelegates }: the amount precondition lives in scope (so an amount at the threshold under "above" is NOT_APPLICABLE). With `any`, PASS if at least one counted approver meets the grade, even if others are unknown; FAIL if all approvers have known grades below it; otherwise NOT_EVALUABLE. With `all`, any unknown grade makes it NOT_EVALUABLE. Exited approvers and system actors are not counted. Evidence states the source of every grade (transaction or master snapshot).
   379→- `approval_count` { minDistinct, requiredRoles[] }: distinct people; roles resolved from the transaction role field, the employee master roles or the management chain (line manager); unresolvable role information gives NOT_EVALUABLE.
   380→- `approval_chain` { mustInclude: line_manager | receiving_manager | within_depth(n) }: management graph from the employee master; cycles give DQ-010 and NOT_EVALUABLE.
   381→- `segregation_of_duties` { forbiddenPairs: [requester, approver] | [beneficiary, approver] | [requester, beneficiary] }: compares canonical person IDs; NOT_EVALUABLE if a needed person field is missing.
   382→- `required_documents` { required[], conditions }: missing set = required − normalised attached set; FAIL lists every missing document; documents column absent or condition fact missing gives NOT_EVALUABLE; unrecognised attachments appear as caveats and never count.
   383→- `timing_window` { fromFact, toFact, maxDays|minDays, basis calendar|business, inclusive }: signed day difference in Asia/Dubai; business days use the versioned calendar; a date outside the calendar gives DQ-015.
   384→- `sequence` { order[], strict }: compares instants, or dates at day precision with a caveat when either side lacks a time.
   385→- `eligibility` { allowedStatuses, exemptTypes, probationDays }: point-in-time status derived from employment spells at the effective date; active through the exit date inclusive.
   386→- `aggregate_limit` { windowDays, metric count|sum, max, groupBy, anchor: effectiveDate }: for each transaction, the window [anchor − windowDays + 1, anchor] in effective-date order (ties broken by submission time, then row ID); a transaction FAILs when the running total including it exceeds the maximum; evidence lists contributing IDs.
   387→- `duplicate` { keys[], toleranceDays, ignoreReversals, flag: later|both }: the default `later` flags the later twin (effective date, then submission time, then row ID) and cites the earlier one; choose `later` or `both` from the worked examples and record an ADR.
   388→- `reference_integrity` { facts[], activeAt: effective|approval }: FAIL when a referenced person does not exist or is inactive at the reference time.
   389→- `value_bounds` { fact, min?, max?, pctOf?, pctMax? }: a percentage needs a known base; an unknown base gives NOT_EVALUABLE unless it can be derived from earlier transactions, which the evidence states.
   390→
   391→**Clauses.** A rule with several requirements (a), (b) emits one result per clause, with clause IDs `C1`, `C2` and so on in the order of the text. A family never emits one result per list item (for example, one exception lists all missing documents).
   392→
   393→**Precedence and conflicts.** Overlapping scopes with opposite outcomes are detected at compile time; the pack must declare precedence (specific over general), and the interpretation record shows it.
   394→
   395→**Compilation.** Specs compile to typed closures (no `eval`, no dynamic code), validated against the fact catalogue. A pack is the sorted set of specs, calendar references, ladders and synonyms; `packHash` = SHA-256 of its canonical JSON.

   412→# 11. DETECTION ENGINE
   413→
   414→## Spec · PRD §11 Detection engine and outcome semantics
   415→
   416→- A pure TypeScript package: no I/O, no wall clock, no randomness, integer money, canonical JSON hashing (RFC 8785) and stable sorting.
   417→- Evaluation order per transaction and rule: scope check (not applicable) → data sufficiency (not evaluable) → check (pass or fail) → evidence record.
   418→- All four outcomes are stored, which makes the coverage matrix possible: rows are rules, columns are outcome counts, and every cell drills down to transactions.
   419→- Census proof banner, with every number clickable (illustrative figures): "10,000 transactions × 18 rules = 180,000 checks · 41,220 applicable · 40,964 evaluated · 256 not evaluable · 312 failed".
   420→- **Flood guard.** If a rule's fail rate in a run exceeds the larger of 3× its backtest baseline or baseline + 2 percentage points, its new exceptions are held rather than routed and the rule owner is alerted. The run still completes and the hold is visible.
   421→- **Precision safeguards.** Scope preconditions on every rule, normalisation tests, a near-miss suite and grouping by root cause. One approver self-approving 9 transactions produces 9 exceptions in one group.
   422→- **Performance.** 10,000 × 20 in ≤ 10 seconds end to end on a laptop; 1,000,000 transactions in ≤ 10 minutes across 16 shards.
   423→- **Run manifest.** Engine version, rule pack hash, calendar hash, configuration hash, input file hashes, counts and output hash. Two runs on the same inputs produce the same output hash.
   424→
   425→**Signature.** `evaluate(input: { transactions, employeeIndex, pack, calendar, config, asOf, shard? }) → { results: CheckResult[], counts, outputHash }`. It is pure, synchronous per shard and returns `Result` values; it never throws for business outcomes. A failing rule module yields NOT_EVALUABLE with a reason, never an aborted run.
   426→
   427→**Algorithm.** Pre-index employees (spells, ladder ordinals, management graph with cycle detection) and per-employee transaction lists sorted by effective date. For each transaction in row-ID order and each rule in rule-ID then clause-ID order: select the rule version by its date basis → scope (NOT_APPLICABLE) → data sufficiency (NOT_EVALUABLE with DQ codes) → check (PASS or FAIL) → evidence → evidence hash. Shard by `hash(employeeId) mod 16` so aggregate and duplicate rules stay within a shard. `outputHash` = SHA-256 over the sorted tuples (rowId, ruleId, clauseId, outcome, evidenceHash).
   428→
   429→**Run pipeline.** `POST /runs` (or the CLI) → `run.evaluate.shard` jobs writing to a run-scoped staging partition → `run.finalize` (fencing check, census completeness, determinism sample, flood guard, routing hold, not-evaluable spike guard, idempotent exception upsert, observations, outbox rows, manifest, projection version bump) in one transaction. The as-of date is an explicit input; the CLI default is the day after the latest date in the dataset, recorded in the manifest.
   430→
   431→**Export.** Only FAIL results become findings in the official file. NOT_EVALUABLE results go to `data_quality.csv` in the same bundle. The exporter uses the ExportProfile learned from `finding_format.csv` (column order, enumerations, ID and date formats, encoding, line endings), is byte-deterministic, and passes the export validator (FS-20) before the file can be downloaded.

   686→## Spec · Platform §3 Request lifecycle
   687→
   688→Middleware runs in this order on every request:
   689→
   690→1. Assign or accept `X-Request-Id`; start the trace span; attach the correlation ID to the log context.
   691→2. Authenticate (session cookie or service token). Reject with `MZ-AUTH-401`.

   862→## Spec · Platform §9 Concurrency and consistency
   863→
   864→- Optimistic concurrency on exceptions and rule drafts through `version` and `If-Match`. No last-writer-wins anywhere.
   865→- Every command writes, in one transaction: the state change, an audit event appended to the hash chain, and an outbox row. Either all three exist or none do.
   866→- Read-your-writes: command responses return the new version and event hash; the client updates from that response, not from a refetch race.
   867→- Monotonic reads for run status: the client discards any status older than the one it holds.
   868→- The audit chain orders events by a database sequence, never by wall-clock time. Each event stores `prev_hash` and `hash = SHA-256(prev_hash ‖ canonical_json(event))`.

   888→
   889→- **Sharding.** Evaluation shards by `hash(employee_id) mod 16` so per-employee aggregate and duplicate rules stay inside one shard.
   890→- **Leases and fencing.** A job holds a lease with a heartbeat every 10 s. Losing the lease increments `lease_epoch`; finalize refuses to write with a stale epoch.
   891→- **Poison messages.** After the final attempt a job moves to `dlq.<queue>` with payload, error chain and trace ID. `mizan dlq list | show <id> | replay <id> | replay --all --since <time>` re-enqueues after a fix, and replay is safe because every job is keyed.
   892→- **Outbox relay.** Polls `outbox` with `SKIP LOCKED` in batches of 100, publishes, then marks sent. Consumers dedupe through the inbox table.
   893→- **Backpressure.** At most 2 in-flight runs per tenant. When queue depth implies a wait above 60 s, new run requests get `429` with a computed `Retry-After`, and the UI shows "Queued: 2 runs ahead, about 40 s".
   894→- **Load-shedding order.** Narrative polish → pattern detection → analytics refresh (dashboards labelled stale) → backtests and archive → evidence packs deferred with an ETA. **Never shed:** ingestion, evaluation, finalize, decisions, audit writes, deadline ticks, integrity verification.

   896→## Spec · Platform §11 Retries and exponential backoff
   897→
   898→One shared helper, used everywhere. Full jitter: `delay = random(0, min(cap, base × 2^(attempt − 1)))`, raised to `Retry-After` when the server provides it, and never beyond the overall deadline.
   899→
   900→| Dependency | Base | Cap | Max attempts | Overall deadline | Retry on | Never retry on |
   901→| --- | --- | --- | --- | --- | --- | --- |
   902→| Postgres (whole transaction) | 50 ms | 1 s | 5 | 3 s interactive, 60 s batch | Serialisation failure 40001, deadlock 40P01, connection reset | Constraint violations, syntax, permission |
   903→| Object store | 200 ms | 5 s | 5 | 30 s | Timeouts, 429, 500, 502, 503, 504, connection reset | 400, 403, 404 on a content-addressed key |
   904→| LLM gateway | 500 ms | 8 s | 3 interactive, 4 queued | 8 s / 15 s | Timeouts, 429, 5xx | Schema-invalid output (fall back instead), 400 |
   905→| Notifications | 5 s | 15 min | 8, then dead-letter | 2 h | Timeouts, 429, 5xx | 4xx except 408 and 429 |

   907→
   908→**Retry budget.** Each dependency has a token bucket: every first-attempt call adds 0.1 tokens (maximum 10) and every retry spends 1. Retries therefore stay under 10% of traffic, and a failing dependency gets fast failures instead of a retry storm.
   909→
   910→    // packages/reliability/src/retry.ts — the only retry implementation in the repo.
   911→    export interface RetryPolicy {
   912→      name: 'postgres' | 'objectStore' | 'llm' | 'notify' | 'http';
   913→      baseMs: number;
   914→      capMs: number;
   915→      maxAttempts: number;   // includes the first attempt
   916→      deadlineMs: number;    // across all attempts
   917→      retryOn: (e: unknown) => boolean;
   918→    }
   919→
   920→    export async function withRetry<T>(
   921→      policy: RetryPolicy,
   922→      op: (attempt: number, signal: AbortSignal) => Promise<T>,
   923→      ctx: RetryContext, // { signal, budget, rng, now, sleep, log } injected for determinism in tests
   924→    ): Promise<T> {
   925→      const startedAt = ctx.now();
   926→      let last: unknown;
   927→      for (let attempt = 1; attempt <= policy.maxAttempts; attempt++) {
   928→        const remaining = policy.deadlineMs - (ctx.now() - startedAt);
   929→        if (remaining <= 0) break;
   930→        const controller = new AbortController();
   931→        const timer = setTimeout(() => controller.abort(new DeadlineExceeded(policy.name)), remaining);
   932→        const relay = () => controller.abort(ctx.signal?.reason);
   933→        ctx.signal?.addEventListener('abort', relay, { once: true });
   934→        try {
   935→          const result = await op(attempt, controller.signal);
   936→          if (attempt === 1) ctx.budget.deposit(policy.name);
   937→          return result;
   938→        } catch (error) {
   939→          last = error;
   940→          const canRetry = policy.retryOn(error) && attempt < policy.maxAttempts && ctx.budget.withdraw(policy.name);
   941→          ctx.log.warn({ dependency: policy.name, attempt, retrying: canRetry, code: errorCode(error) });
   942→          if (!canRetry) throw new DependencyError(policy.name, attempt, { cause: error });
   943→          const ceiling = Math.min(policy.capMs, policy.baseMs * 2 ** (attempt - 1));
   944→          const jittered = Math.floor(ctx.rng() * ceiling);
   945→          const delay = Math.max(jittered, retryAfterMs(error) ?? 0);
   946→          const left = policy.deadlineMs - (ctx.now() - startedAt);
   947→          await ctx.sleep(Math.min(delay, Math.max(0, left)), ctx.signal);
   948→        } finally {
   949→          clearTimeout(timer);
   950→          ctx.signal?.removeEventListener('abort', relay);
   951→        }
   952→      }
   953→      throw new DependencyError(policy.name, policy.maxAttempts, { cause: last });
   954→    }
   955→
   956→## Spec · Platform §12 Circuit breakers, bulkheads and timeouts
   957→
   958→- **Circuit breakers** on the LLM gateway, object store, notification channel and Valkey. Closed → open when ≥ 50% of at least 20 calls fail within 30 s, or after 5 consecutive timeouts. Open for 30 s, then half-open with 3 probes; success closes it, failure reopens it with the open period doubling up to 5 minutes. Breaker state is a metric and drives the mode banner.
   959→- **Bulkheads.** Separate connection pools: interactive role (20 connections, `statement_timeout` 3 s) and batch role (10 connections, 120 s). Separate worker pools for warm and cold queues, so a backtest never starves a decision.
   960→- **Timeouts, all explicit.**

   972→## Spec · Platform §13 Error handling discipline
   973→
   974→- Typed errors only: `ValidationError`, `AuthError`, `ConflictError`, `DependencyError`, `DeadlineExceeded`, `InvariantViolation`, each carrying an `MZ-` code, `retryable` flag and `cause`.
   975→- The engine never throws for business outcomes. It returns `Result<Outcome, EngineError>`; a failing rule becomes `NOT_EVALUABLE` with a reason, never an exception that aborts the run.
   976→- **No bare catch.** Every `catch` does one of three things: handle with a typed fallback, translate and rethrow with `cause`, or record and rethrow. Swallowing an error is a lint failure.
   977→- `finally` releases resources: timers, listeners, locks, file handles, leases.
   978→- `InvariantViolation` (for example, an audit hash mismatch or an evidence hash that does not reproduce) opens an integrity incident and moves the system to safe halt. It is never retried.
   979→- Unhandled rejections and uncaught exceptions crash the process after flushing telemetry; the orchestrator restarts it. Silent zombie processes are worse than restarts.
   980→- HTTP mapping is centralised in one error handler that emits problem details and never leaks stack traces or SQL.

  1047→

  1053→            │ workers     │                     │ workers     │   both pull from the same queue
  1054→            │ Valkey (A)  │                     │ Valkey (B)  │   caches: per site, disposable
  1055→            │ PG primary ─┼──── synchronous ────┼─► PG standby│   one writer at a time

  1059→
  1060→- **What is active-active.** Web, API and workers run in both sites and serve traffic at the same time. Workers in both sites claim jobs from the same Postgres queue; `SKIP LOCKED` distributes work without coordination.
  1061→- **What is single-writer.** Postgres has one primary at a time with a synchronous standby in the other site (Patroni or a managed high-availability service) and a witness for quorum. This is a deliberate choice: audit trails and human decisions must have one order.
  1062→- **Why duplicate work is harmless.** The engine is deterministic and every write is an idempotent upsert keyed by content, so a job that runs in both sites during a failover produces identical rows. Fencing tokens stop a worker that lost its lease from writing.
  1063→- **Split-brain prevention.** Only the elected leader accepts writes. The application checks `pg_is_in_recovery() = false` on connection checkout for the write pool.
  1064→- **Idempotency keys** live in Postgres, so they survive failover; Valkey is only a fast path.
  1065→- **Clocks.** NTP everywhere; ordering by database sequence; timestamps are informational.
  1066→- **Targets.** RPO 0 for Postgres (synchronous commit); RTO ≤ 5 minutes for API and workers; object store replication lag ≤ 15 minutes; point-in-time recovery for 35 days; monthly restore drill into a clean environment.
  1067→- **Failover drill (demo-able).** Kill the Site A primary mid-run. Writes pause briefly with `MZ-MODE-503` and `Retry-After: 5`, Site B is promoted, the run resumes from its checkpoint, and the output hash matches the control run.

  1073→# 25. OPERATING MODES, FLAGS AND FAILSAFES
  1074→
  1075→## Spec · Edge cases §1 Failure philosophy
  1076→
  1077→1. **Fail closed on integrity, fail open on convenience.** If correctness is in doubt, stop writing. If a convenience breaks (the model, the cache, a chart), drop it and keep going.
  1078→2. **Every check ends somewhere.** Each transaction × rule pair ends as PASS, FAIL, NOT_APPLICABLE or NOT_EVALUABLE. A run publishes completely or not at all.
  1079→3. **Never invent a fact.** Missing or ambiguous data produces NOT_EVALUABLE with a data-quality code. A default may influence an outcome only when the evidence carries a caveat that states it.
  1080→4. **Hold routing before holding detection.** Suspicious volumes pause notifications, not evaluation.
  1081→5. **Every mode is visible.** A mode chip in the top bar, a banner in plain language, `GET /api/v1/system/mode`, the metric `mizan_mode` and an audit event on every transition.
  1082→6. **People clear the serious modes.** Safe halt clears only when an administrator gives a reason, verification passes and a second administrator countersigns.
  1083→7. **Shed in a fixed order.** Narrative polish, then pattern detection, analytics refresh, backtests and archive, and finally evidence packs, which are deferred rather than dropped. Ingestion, evaluation, finalize, decisions, audit writes, deadline ticks and integrity verification are never shed.
  1084→8. **Safety controls are code, not configuration.** Flags can restrict behaviour. No flag can relax a safety control.

  1130→## Spec · Edge cases §3 Mode controller
  1131→
  1132→- A controller loop in each API region evaluates health signals every 10 s. It writes the current mode to `system_mode` in Postgres, the source of truth, with one row per tenant and region holding the version, reason, signals and start time. It publishes `mode.changed` through the outbox and writes an audit event.
  1133→- **Hysteresis.** A mode is entered after 3 consecutive bad readings (30 s) and exited after 6 consecutive good readings (60 s), with a minimum dwell of 2 minutes. M5 is entered on the first failure and M4 immediately on failover.
  1134→- **Reading the mode.** Services subscribe through Valkey pub/sub and poll Postgres every 5 s as a fallback. A service that cannot read the mode for 15 s behaves as M4 for writes (fail closed) and keeps serving reads.
  1135→- **Operator overrides.** `mizan mode set read-only --reason "…" --ttl 30m`. Every override needs a reason and a time-to-live of at most 24 hours. It appears in the audit trail, and the banner says it was set by an administrator.
  1136→- **Entering M5 never deletes or rewrites data.** It records a pointer to the first failing chain segment.

  1278→## Spec · PRD §17 Responsible AI
  1279→
  1280→| Use | Where | Data the model sees | Guard | Fallback |
  1281→| --- | --- | --- | --- | --- |
  1282→| Rule drafting | Rule studio | The author's sentence and the fact catalogue, no transactions | Schema validation, template back-rendering, tests, backtest, two-person approval | Guided builder |
  1283→| Narrative polish | Exception detail | One exception's evidence record with pseudonymous IDs | Fact-lock, banned terms, length limits | Canonical template |
  1284→| Pattern alerts | Patterns page | None; deterministic statistics | Protected attributes excluded; human review | Not applicable |
  1285→
  1286→- **Human decision on every exception**, with a countersign for High and Critical dismissals. A model cannot change state.
  1287→- **Transparency.** Every exception shows the rule, clause, evidence and how the rule is read. The product says when text was polished by a model.
  1288→- **Contestability.** Owners can dispute an exception with a reason; disputes feed rule review.
  1289→- **Data minimisation.** Models never receive datasets, only one evidence record or one sentence at a time.
  1290→- **Fairness.** Disparity monitoring across departments and locations; patterns exclude protected attributes; small cells suppressed.
  1291→- **Default deployment.** AI off, or a local model inside the environment. Nothing is sent to services that keep or train on data.
  1292→- **Limitations stated.** Rule interpretation can be wrong, snapshot master data can lag reality, and patterns indicate risk, not wrongdoing.
  1293→
  1294→**Responsible-AI statement (for the solution note).** MIZAN decides whether a transaction is an exception using deterministic, versioned rules that people wrote, tested and approved; AI never makes, changes or closes that decision. AI is optional and used in two places only: drafting a rule from plain English, which a person reviews, tests against history and a second person approves; and phrasing explanations, which are checked against the underlying evidence before display and fall back to a fixed template if any detail does not match. Every exception carries its rule, rule version, the exact data behind it and a named owner, and every exception is decided by a person. Nothing is changed in any HR system. All actions are recorded in a tamper-evident audit trail. The prototype processes only the synthetic pack, locally, and sends nothing to services that retain or train on data. Pattern alerts exclude protected characteristics and are reviewed by a person before reaching anyone else.

  1296→## Spec · PRD §16.4 Employee experience and fairness principles
  1297→
  1298→1. **Transactions, not people.** Exceptions describe a process gap. Copy never implies intent.
  1299→2. **Good faith by default.** Most exceptions are process errors and the language treats them that way.
  1300→3. **No surprises.** If a correction will change an employee's pay, record or leave, the owner informs the employee before the change, using a bilingual template that explains what happened, what changes and when.
  1301→4. **Right to respond.** The employee can add context through HR, and it is attached to the exception and the trail.
  1302→5. **Proportionate response.** Low and Medium exceptions are coaching and process fixes. Any people-related consequence follows existing HR procedures, outside MIZAN.
  1303→6. **Fix harm first.** Employee-impacting exceptions such as underpayment are prioritised to be fixed before the next payroll.
  1304→7. **Consistency.** The same rule applies to everyone. Exception rates by department and location are monitored for unexplained disparity.
  1305→8. **Privacy.** People see the minimum necessary data. Team dashboards suppress small cells.
  1306→9. **Human decision.** No exception affects anyone until a person decides.
  1307→10. **Bilingual by default.** Employees are addressed in their preferred language.

  1888→# 33. TESTING AND BACKTESTING
  1889→
  1890→## Spec · Backtesting §1 What accuracy means here
  1891→
  1892→- Judges count planted violations we find and false positives we raise. Each false positive also costs credibility in the explanation and routing score, because every flag must be defended.
  1893→- **Precision first, then recall.** A rule only fires when its scope, data sufficiency and check all hold. Ambiguous data becomes "not evaluable" with a data-quality exception, which is not exported as a policy finding unless the worked examples show that category.
  1894→- **Unit of scoring:** one row per transaction and rule pair, unless the five worked examples in `finding_format.csv` show a different grain. The export adapter follows the examples exactly.
  1895→- **Traps to expect in planted data:** values exactly at thresholds, intervals exactly at window limits, allowed delegations, document synonyms and odd casing, weekends and holidays, approvers promoted or exited around the approval date, duplicate IDs, and transactions that break two rules at once.
  1896→
  1897→## Spec · Backtesting §2 Sources of truth without an answer key
  1898→
  1899→| Source | What it is | What it catches |
  1900→| --- | --- | --- |
  1901→| Golden examples | The 5 worked examples from `finding_format.csv`, reproduced exactly | Format, grain, ID and wording conventions |
  1902→| Interpretation records | For each rule: verbatim text, reading, ambiguities, decision, boundary cases; reviewed by a second person | Misreading the policy |
  1903→| Mutation labels | Seeded injections of known violations, each with a near-miss twin that must not fire | Recall gaps and false positives at boundaries |
  1904→| Independent oracle | Every rule re-implemented in SQL on DuckDB by a different author from the rule text, with its own parsing | Engine and normalisation bugs |
  1905→| Metamorphic invariants | Transformations that must leave results unchanged, or change them predictably | Hidden dependence on order, format or IDs |
  1906→| Hand-labelled sample | Stratified sample of engine findings labelled by two reviewers | Real-world precision with a confidence interval |
  1907→
  1908→## Spec · Backtesting §3 Harness
  1909→
  1910→    mizan bench golden                         # reproduce the 5 worked examples, column by column
  1911→    mizan bench mutate --seed 42 --per-rule 50 # write mutated datasets + labels.jsonl (positives and near-miss twins)
  1912→    mizan bench format --seed 42               # label-preserving format mutations
  1913→    mizan bench score --labels labels.jsonl --findings out/findings.csv
  1914→    mizan bench oracle                         # DuckDB SQL oracle vs engine, full dataset and all mutated sets
  1915→    mizan bench metamorphic                    # run MR-1 … MR-7
  1916→    mizan bench determinism --runs 2           # byte-identical output across runs and machines
  1917→    mizan bench shift --train data/transactions.csv --test data/transactions_test.csv
  1918→    mizan bench perf --scale 10k,100k,1m
  1919→    mizan bench report                         # writes reports/<date>/backtest.md and backtest.json

  1964→## Spec · Backtesting §6 Metamorphic relations
  1965→
  1966→- **MR-1** Row permutation leaves output bytes unchanged after canonical sorting.
  1967→- **MR-2** A consistent relabelling of employee IDs leaves output unchanged apart from the relabelling.
  1968→- **MR-3** Adding transactions for a new, unrelated employee leaves existing findings unchanged.
  1969→- **MR-4** Scaling every amount below the smallest threshold removes every approval-limit finding and nothing else.
  1970→- **MR-5** Shifting all dates by whole weeks on a holiday-free calendar leaves output unchanged.
  1971→- **MR-6** Removing one rule from the pack leaves every other rule's findings unchanged.
  1972→- **MR-7** Uploading the same file twice creates one dataset and no new exceptions.

  1974→## Spec · Backtesting §7 Property-based tests
  1975→
  1976→Using fast-check generators for valid transactions per family:
  1977→
  1978→- Raising an amount never turns an approval-limit FAIL into PASS.
  1979→- Raising an approver's grade never turns PASS into FAIL.
  1980→- Adding a required document never turns PASS into FAIL.
  1981→- Adding an independent approver never creates a segregation-of-duties failure.
  1982→- Every evaluation returns exactly one of the four outcomes.
  1983→- The evidence record contains every fact the check read.
  1984→- Evaluating twice gives identical outcome and evidence hashes.

  1986→## Spec · Backtesting §8 Independent oracle
  1987→
  1988→1. A different author (or a separate agent session with no access to engine code) implements each rule in SQL over DuckDB from the RuleSpec text and interpretation record only.
  1989→2. The oracle reads the raw CSV with its own explicit parsing rules. It shares only the documented mapping tables (header synonyms, document synonyms, grade ladder, calendar).
  1990→3. `mizan bench oracle` compares the sets of failing (transaction, rule) pairs on the training data and every mutated dataset.
  1991→4. Any disagreement is triaged: re-read the rule, decide the correct reading, fix the wrong side, add a regression case, and update the interpretation record if the reading was clarified.
  1992→5. Gate: zero disagreements.
