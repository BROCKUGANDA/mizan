🛡️

MIZAN fails safe and never fails silently. When something breaks, it narrows what it does instead of guessing. It holds routing before it stops detecting, stops writing before it writes anything it cannot prove, and always shows which mode it is in and why. This page defines the health modes and operating profiles, the degradation ladder, kill switches, 24 failsafes, 8 runbooks and a catalogue of 180 edge cases, each with its expected behaviour and the test that proves it.

## 1. Failure philosophy

1. **Fail closed on integrity, fail open on convenience.** If correctness is in doubt, stop writing. If a convenience breaks (the model, the cache, a chart), drop it and keep going.
2. **Every check ends somewhere.** Each transaction × rule pair ends as PASS, FAIL, NOT_APPLICABLE or NOT_EVALUABLE. A run publishes completely or not at all.
3. **Never invent a fact.** Missing or ambiguous data produces NOT_EVALUABLE with a data-quality code. A default may influence an outcome only when the evidence carries a caveat that states it.
4. **Hold routing before holding detection.** Suspicious volumes pause notifications, not evaluation.
5. **Every mode is visible.** A mode chip in the top bar, a banner in plain language, `GET /api/v1/system/mode`, the metric `mizan_mode` and an audit event on every transition.
6. **People clear the serious modes.** Safe halt clears only when an administrator gives a reason, verification passes and a second administrator countersigns.
7. **Shed in a fixed order.** Narrative polish, then pattern detection, analytics refresh, backtests and archive, and finally evidence packs, which are deferred rather than dropped. Ingestion, evaluation, finalize, decisions, audit writes, deadline ticks and integrity verification are never shed.
8. **Safety controls are code, not configuration.** Flags can restrict behaviour. No flag can relax a safety control.

## 2. Health modes and operating profiles

There are two independent axes. Health modes are entered automatically, or by an operator, in response to failures, and exactly one is current. Operating profiles are configured contexts, and several can be active at once.

### 2.1 Health modes

| ID | Mode | Entered when | Behaviour | Users see | Exit |
| --- | --- | --- | --- | --- | --- |
| M0 | Normal | All health signals green | Full service | Mode chip hidden | — |
| M1 | Degraded AI | Model gateway breaker open; p95 latency above 8 s for 5 min; cost cap reached; load shedding step 1; kill switch; or `ai.mode=none` | Canonical template explanations only; the rule studio uses the controlled grammar and guided builder; no `explain.narrative` jobs are queued | Info banner: "Explanations are shown from approved templates. Narrative polish is off." | 3 consecutive successful half-open probes, cost window reset, load back to normal, or switch cleared |
| M2 | Degraded analytics | Projection lag above 5 min; `analytics.refresh` shed; or read replica unavailable | Dashboards served from the last good projection with an "as of" label; pattern detection paused; queue and decisions unaffected | Stale label on affected panels: "Showing results from 10:14 GST" | Lag under 60 s for 5 consecutive minutes |
| M3 | Degraded storage | Object store health check fails 3 times in 60 s | Uploads, evidence packs and cold reads return `MZ-DEP-503` with `Retry-After`; runs on datasets already ingested continue | Warning banner for analysts and administrators: "File uploads and evidence packs are paused. Decisions still work." | 3 consecutive healthy checks and pending uploads drained |
| M4 | Read-only | Database failover in progress; planned maintenance; disk guard; or operator switch | All writes return `MZ-MODE-503` with `Retry-After`; drafts kept in local storage; SLA clocks paused and the window credited | Warning banner; decision bar disabled with the reason | Primary writable and fencing epoch advanced, or maintenance closed by the operator |
| M5 | Safe halt | `integrity.verify` fails; rule pack hash mismatch at run start; determinism self-check fails; `MZ-INT-500` on a write path; or operator switch | New runs and decisions blocked with `MZ-RUN-423`; reads and audit exports continue; integrity incident opened; administrators and the compliance lead notified | Danger banner: "Evaluation halted: an integrity check failed. No new exceptions will be created until this is resolved." | An administrator clears it with a reason after verification passes, a second administrator countersigns, and the system passes through M4 for one verification run |

Precedence is M5 > M4 > M3 > M2 > M1 > M0. When several conditions are active, the chip shows the most severe one and its tooltip lists the others with their start times.

## 3. Mode controller

- A controller loop in each API region evaluates health signals every 10 s. It writes the current mode to `system_mode` in Postgres, the source of truth, with one row per tenant and region holding the version, reason, signals and start time. It publishes `mode.changed` through the outbox and writes an audit event.
- **Hysteresis.** A mode is entered after 3 consecutive bad readings (30 s) and exited after 6 consecutive good readings (60 s), with a minimum dwell of 2 minutes. M5 is entered on the first failure and M4 immediately on failover.
- **Reading the mode.** Services subscribe through Valkey pub/sub and poll Postgres every 5 s as a fallback. A service that cannot read the mode for 15 s behaves as M4 for writes (fail closed) and keeps serving reads.
- **Operator overrides.** `mizan mode set read-only --reason "…" --ttl 30m`. Every override needs a reason and a time-to-live of at most 24 hours. It appears in the audit trail, and the banner says it was set by an administrator.
- **Entering M5 never deletes or rewrites data.** It records a pointer to the first failing chain segment.

```mermaid
stateDiagram-v2
  [*] --> M0
  M0 --> M1: model breaker open, cost cap, load or switch
  M1 --> M0: 3 healthy probes
  M0 --> M2: projection lag over 5 min
  M2 --> M0: lag under 60 s for 5 min
  M0 --> M3: object store unhealthy
  M3 --> M0: 3 healthy checks
  M0 --> M4: failover, maintenance or disk guard
  M4 --> M0: primary writable and epoch advanced
  M0 --> M5: integrity failure
  M1 --> M5: integrity failure
  M2 --> M5: integrity failure
  M3 --> M5: integrity failure
  M4 --> M5: integrity failure
  M5 --> M4: cleared and countersigned
```

**Run statuses.** `QUEUED` → `RUNNING` → `FINALIZING` → one of `COMPLETED`, `COMPLETED_WITH_HOLDS` (flood guard or routing hold), `COMPLETED_WITH_DQ` (not-evaluable spike or quarantined rows), `FAILED` (nothing published, nothing routed) or `CANCELLED`. A failed run can be retried and keeps its run key, so the retry never duplicates anything.

## 4. Degradation ladder

| Step | Trigger | Action | Users see |
| --- | --- | --- | --- |
| 1 | Worker CPU above 75% for 2 min, or queue wait above 60 s | Stop `explain.narrative` and enter M1 with reason "load" | Template explanations and the Degraded AI banner |
| 2 | Trigger still present after 2 min | Pause `patterns.detect` | Patterns tab: "Paused under load. Resumes automatically." |
| 3 | Still present | Pause `analytics.refresh` and enter M2 | Stale labels on dashboards |
| 4 | Still present | Pause `backtest.run` and `archive.cold` at their next checkpoint | "Backtest queued under load, about 6 min" |
| 5 | Still present | Defer `evidence.pack` with an ETA | "Evidence pack queued, ready by about 14:20" |
| 6 | Run queue wait above 60 s | Admission control: new runs return `MZ-RATE-429` with a computed `Retry-After` | "Queued: 2 runs ahead, about 40 s" |
| Never shed | — | Ingestion, evaluation, finalize, decisions, audit writes, deadline ticks, integrity verification | — |

Recovery reverses the ladder one step every 2 minutes once the trigger clears.

## 5. Kill switches and flags

| Flag | Default | Who can change it | Effect |
| --- | --- | --- | --- |
| `ai.mode` (`none`, `local`, `provider`) | `none` in the judge and air-gapped profiles unless a local model is configured; otherwise as deployed | Administrator | Selects the model gateway backend; `none` forces M1 |
| `ai.narrative.enabled` | `true` | Administrator | Turns narrative polish off without affecting rule authoring |
| `ai.authoring.enabled` | `true` | Administrator or policy owner | Turns model-assisted rule drafting off; the grammar and guided builder remain |
| `routing.enabled` | `true` | Compliance lead | Global routing hold: findings recorded, nothing routed, banner for leads |
| `notifications.email.enabled`, `notifications.webhook.enabled` | `true` | Administrator | Turns a channel off; in-app notifications continue |
| `rule.<id>.hold` | `false` | Rule owner or compliance lead | Holds routing for one rule (a manual flood guard) |
| `runs.enabled` | `true` | Administrator | Blocks new runs with `MZ-RUN-423` |
| `patterns.enabled` | `true` | Compliance lead | Turns pattern detection off |
| `uploads.enabled` | `true` | Administrator | Blocks uploads |
| `exports.findings.enabled` | `true` | Compliance lead | Blocks the findings export |
| `bulk.enabled` | `true` | Compliance lead | Turns bulk decisions off |
| `flood_guard.multiplier`, `flood_guard.min_pp` | `3`, `2` | Compliance lead | Tunes the flood guard within bounds (multiplier 2–5, percentage points 1–5) |
| `mode.override` | none | Administrator | Forces a health mode, with a reason and a time-to-live |

**Mechanics.** Flags live in the Postgres `feature_flag` table, versioned and audited, and every change needs a reason. They are cached in Valkey for 5 s, read at the start of each job and pinned in the run manifest, and a change takes effect within 10 s. Settings shows who changed what and when.

**Not switchable (code invariants).** The conflict-of-interest guard; the two-person rule for rule approval; countersign for High and Critical dismissals; a human decision before closure; hash-chained audit writes; fact-lock on model text; row-level security; log redaction; the synthetic-only guard in judge mode; and the engine's isolation from the model.

## 6. Failsafes

| ID | Failsafe | Protects against | Mechanism | Proven by |
| --- | --- | --- | --- | --- |
| FS-01 | Atomic run publish | Half-written runs | Shards write to a run-scoped staging partition; finalize validates and swaps it in within one transaction; a crash leaves the run `FAILED` with nothing routed | Chaos: kill a worker and then the finalizer mid-run |
| FS-02 | Census completeness | Silently skipped checks | Finalize asserts one outcome for every transaction × active-rule pair, by count and by a hash of the pair set; a mismatch fails the run with `MZ-INT-500` | Property test; fault injection drops one result |
| FS-03 | Determinism self-check | Hidden non-determinism | A seeded 1% sample is re-evaluated on a different worker and the evidence hashes must match; a mismatch enters M5 | Inject a clock read or unordered map iteration |
| FS-04 | Pinned inputs | Rules, calendars or configuration changing mid-run | The run manifest pins the rule pack, calendar, routing table, grade ladder, synonym tables and flags by hash; a worker holding a different hash refuses the shard | Change the pack during a run |
| FS-05 | Flood guard | Mass false positives from a format break | Per rule: a fail rate above the larger of 3× baseline or baseline + 2 percentage points holds new exceptions from routing and alerts the rule owner | Swap the day-month order in a fixture |
| FS-06 | Run-level routing hold | Routing storms | New exceptions in one run above 5% of transactions or above 2,000 hold the whole run until a compliance lead releases it; exports are unaffected | Mutate 10% of rows |
| FS-07 | Not-evaluable spike guard | Data drift hiding breaches | A rule with NOT_EVALUABLE above 5% of applicable checks, or above 3× its baseline, sets the run to `COMPLETED_WITH_DQ`, surfaces the mapping review and creates a stewardship group | Drop a column |
| FS-08 | Quarantine, never drop | Lost rows | Unparseable rows go to quarantine with DQ codes and row numbers; counts appear in the census banner and can be downloaded | Fixture with 12 broken rows |
| FS-09 | Schema fingerprint | Renamed, missing or new columns | The header fingerprint is compared with the saved mapping; unknown columns go to review; missing required columns fail with `MZ-DS-422` before evaluation | Format mutations F-1 to F-9 |
| FS-10 | Idempotency everywhere | Duplicate effects on retry | Idempotency keys on mutating endpoints, job keys, deterministic exception keys, consumer inbox | DLQ replay and double-submit tests |
| FS-11 | Fencing tokens | Split brain and zombie workers | Lease epoch per job; finalize and decisions reject stale epochs; single-writer Postgres with a witness | Pause a worker past its lease, then resume it |
| FS-12 | Transactional outbox | Lost notifications | Notification rows are written in the same transaction as the state change; the relay retries and dead-letters; an in-app copy always exists | Stop the mail relay |
| FS-13 | Audit hash chain | Tampering or silent edits | Each event hashes the previous one; verification runs hourly; a failure enters M5 | Edit one audit row directly |
| FS-14 | Fact-lock | The model inventing facts | Every number, date and ID must exist in the evidence; the rule ID and action are required; banned terms are rejected; otherwise the canonical text is shown | Adversarial narrative suite |
| FS-15 | Data, not instructions | Prompt injection through CSV text | Free text reaches the model only as quoted data; the engine never reads free text for decisions; instruction-like text is tagged DQ-017 for review | Injection fixtures |
| FS-16 | Conflict-of-interest guard | Self-review | Requesters, approvers and beneficiaries cannot decide, verify or countersign; refusals are audited | API and UI tests |
| FS-17 | Two-person rule | One person changing what gets checked | Rule author ≠ approver (`MZ-RULE-403-SELF`); administrator grants need a second administrator | API tests |
| FS-18 | Bulk-decision limits | Mass dismissal | At most 200 items per bulk action; never High or Critical dismissals; preview, typed confirmation and a 10-second undo before submission; one record per item | UI and API tests |
| FS-19 | Activation gate | A mis-specified rule going live | A backtest on the exact spec hash is required; a fail rate above 10% of applicable history needs explicit acknowledgement and a second approver; a shadow run comes first | Rule studio tests |
| FS-20 | Export validator | A malformed submission | The findings file is validated against the finding-format profile, parsed back, and must reproduce the 5 worked examples exactly before export is enabled | Golden tests |
| FS-21 | Clock discipline | Wall-clock dependence and skew | The engine has no clock (as-of is an input); SLA timers use database time; a node skewed more than 2 s from NTP fails readiness | Skew injection |
| FS-22 | Retry budget and breakers | Retry storms | A token-bucket retry budget per dependency keeps retries under 10% of traffic; a breaker per dependency; bulkheads per pool | Dependency fault injection |
| FS-23 | Backup and restore proof | Data loss | Synchronous standby (RPO 0), point-in-time recovery, nightly backups and a weekly automated restore into a scratch database with integrity verification | Restore drill report |
| FS-24 | Synthetic-only guard | Real personal data in a demo | The judge profile rejects untagged datasets; a PII scanner (Emirates ID pattern `784-YYYY-NNNNNNN-N`, passport, phone, email and IBAN patterns) blocks the upload | Upload a fixture containing an Emirates ID pattern |

## 7. Edge-case catalogue

Every case has an ID of the form `EC-<category><number>`, the expected behaviour and the test that proves it. Test types: U unit, P property-based, G golden, I integration, E end-to-end (Playwright), C chaos, MR metamorphic, MUT mutation operator from the backtesting harness, F format mutation, R rehearsal.

## 9. Runbooks

Each runbook follows the same five steps: detect, contain, recover, verify and communicate.

**RB-01 · Model gateway outage**

- Detect: breaker-open alert; `mizan_mode{mode="degraded_ai"}`.
- Contain: M1 is automatic; confirm that no narrative jobs are queued.
- Recover: check the provider's status; switch to `ai.mode=local` if available, otherwise wait while the breaker half-opens every 30 s.
- Verify: 3 probes succeed and the fact-lock pass rate on the probe set is at least 99%.
- Communicate: the banner is automatic; post in the pilot channel if the outage lasts more than 30 minutes.

**RB-02 · Flood guard hold**

- Detect: "R07 held" alert to the rule owner.
- Contain: the hold is automatic, and routing pauses for R07 only.
- Recover: inspect a sample of 20 held exceptions. If the cause is a format break, fix the mapping and re-run. If the spike is real, a compliance lead releases the hold with a reason.
- Verify: the re-run fail rate is back within band, or the release is recorded.
- Communicate: tell the owner teams "R07 exceptions are delayed for review".

**RB-03 · Integrity failure (safe halt)**

- Detect: `integrity.verify` fails and the system enters M5.
- Contain: automatic; freeze administrator role changes and snapshot the database.
- Recover: find the first failing segment and compare it with the immutable object-store copy of the chain. If it was tampered with, restore from the immutable copy and open a security incident.
- Verify: full chain verification passes and one verification run reproduces the last run's output hash.
- Communicate: tell the compliance lead and audit within 1 hour, and record the incident.

**RB-04 · Database failover**

- Detect: primary health check fails and the witness decides.
- Contain: M4; the fencing epoch advances.
- Recover: promote the standby, rebuild a new standby and check replication.
- Verify: write probe succeeds, outbox lag is under 60 s and the idempotency log shows no duplicate decisions.
- Communicate: the banner is automatic; write a post-incident note if it lasted more than 5 minutes.

**RB-05 · Hidden test file surprise (T−72h)**

- Detect: schema fingerprint mismatch, DQ spike, flood guard or not-evaluable spike on the hidden file.
- Contain: freeze the rule pack (O5). Never edit rules to fit the file.
- Recover: fix only mapping and normalisation code, with tests. Every change adds a regression case and reruns the full backtest. Never hand-edit outputs.
- Verify: every gate in the backtesting document passes, determinism is 2 of 2 and the export validator passes.
- Communicate: list every change in the submission notes.

**RB-06 · Dead-letter growth**

- Detect: any message in a non-sheddable DLQ.
- Contain: identify the error class with `mizan dlq list`.
- Recover: fix, deploy, then `mizan dlq replay --all --since <time>`.
- Verify: the DLQ is empty and the replay created no duplicates.
- Communicate: write an incident note if users noticed.

**RB-07 · Notification outage**

- Detect: outbox lag above 5 minutes or channel errors.
- Contain: turn the channel flag off if messages are bouncing; in-app continues.
- Recover: restore the channel; the relay drains the backlog as digests.
- Verify: outbox lag is under 60 s.
- Communicate: administrator banner; tell owners to work from the in-app queue.

**RB-08 · Demo-day failure**

- Detect: anything going wrong on stage.
- Contain: switch to the offline laptop profile. If the laptop fails, play the recorded walkthrough from the same point.
- Recover: Reset, then resume the script from the last checkpoint.
- Communicate: say what happened in one sentence and show the mode banner. The degraded modes are part of the story.

## 10. Making the catalogue enforceable

- `docs/edge-cases.yaml` mirrors section 7 with `id`, `category`, `case`, `expected` and `tests`.
- Each test declares the IDs it covers (`@ec EC-B07`). CI fails if any ID has no test, if a test references an unknown ID, or if expected-behaviour text changes without a matching test change.
- Each failsafe FS-01 to FS-24 has a chaos or integration test tagged `@fs FS-05`. They run nightly and before every release.
- Runbooks are rehearsed: RB-03, RB-04 and RB-05 before submission, and all eight in pilot week 1.
