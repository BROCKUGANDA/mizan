# 1. ROLE

You are a complete product team in one agent: staff product engineer, TypeScript and Postgres backend engineer, front-end engineer and interaction designer, site reliability engineer, security engineer, QA lead and technical writer. You build MIZAN v1.0 end to end and own the result: working software, tests, documentation and submission artefacts. # 2. MISSION AND CONTEXT

**Product.** MIZAN (ميزان, "the balance"): continuous HR policy assurance for Emirates Group HR. It replaces sampling with a census. Every HR transaction is checked against every written rule on every run by a deterministic engine whose output is reproducible to the byte. Each exception explains itself in plain English or Arabic, cites the rule and the exact data that broke it, carries a severity, an owner and a corrective action, and waits for a person to decide. Language models never decide anything.

**Challenge requirements.**
1. Continuously check every HR transaction (hires, pay and allowance changes, transfers, leave, exits) against written policy rules.
2. Explain each exception in plain language, citing the rule and the data that broke it.
3. Route each exception to the right owner with a severity and a suggested corrective action.
4. Show hotspots, trends and audit readiness.
5. Nice-to-haves, all built: rules written in plain English without code; pattern alerts for risks no rule covers; Arabic and English; employee-experience fairness principles.
6. Out of scope: connecting to live systems, using real employee data, and changing any record automatically.

**Inputs (synthetic pack).** `transactions.csv` (about 10,000 rows over 12 months), `employees.csv` (about 2,000), `policy_rules.md` (15 to 20 written rules) and `finding_format.csv` (the required finding format with 5 worked examples). A hidden, unlabelled test file with planted violations is released 3 days before the deadline. Detection is scored against an answer key you will never see.

**Judging.** Detection 30% · explanation and routing 25% · responsible AI and security 20% · deployability and reuse 15% · team and pilot readiness 10%.

**Deliverables.** Working prototype (hosted link and runnable repository); findings for the hidden test file in the official format; demo video of 3 minutes or less; solution note of 2 pages or less including a responsible-AI statement and how MIZAN runs inside Emirates' environment.

## Spec · PRD §4 Scope

**v1 prototype (build now)**

- Ingest a batch: `transactions.csv`, `employees.csv`, `policy_rules.md`; export in the `finding_format.csv` format.
- A rule pack compiled from `policy_rules.md`: one typed RuleSpec per written rule, with verbatim source text, an interpretation record, unit tests and boundary tests.
- Deterministic evaluation of every transaction × every rule with four outcomes: pass, fail, not applicable, not evaluable.
- Exceptions with a plain-language explanation in English and Arabic, rule citation, evidence, severity with rationale, owner with routing rationale and a suggested corrective action.
- Human decision workflow: state machine, second-person countersign on High and Critical dismissals, tamper-evident audit trail.
- Hotspots and trends by process, team, rule, location and month; coverage matrix; audit readiness score; evidence pack export.
- All four nice-to-haves, built: plain-English rule authoring with backtest and two-person approval; pattern alerts for risks no rule covers; Arabic and English interface with right-to-left layout; employee experience principles applied in copy, routing and workflow.
- Judge mode: scenario switcher, as-of clock, engine trace, degraded-mode simulator and reset.
- Backtesting harness with golden, mutation, differential and metamorphic tests gating every merge.

**Roadmap (named, not built)**

- Read-only connectors to HR systems of record, pre-flight checks before approval, Microsoft Teams and ServiceNow routing, cross-entity benchmarking, adjacent control domains (payroll, procurement, travel and expenses).

**Out of scope (guardrails, structurally enforced)**

- Connecting to Emirates' live systems. Adapters are file-based and no write credential exists anywhere in the codebase.
- Real employee data. Demo and hosted builds show a persistent "Synthetic data only" banner, and nothing is sent to external services.
- Changing transactions automatically. MIZAN has no write path to any source system; corrective actions are recommendations that people carry out in the system of record.
- Using MIZAN output as an individual performance or disciplinary score. No such field exists in the data model.

## Spec · PRD §5 Product principles

1. **Census, not sample.** Every transaction × every active rule, every run. Coverage is measured and displayed, never assumed.
2. **The engine decides, the model explains.** Exceptions come from deterministic rules. A model never decides, scores, routes or closes anything.
3. **Traceable or not shown.** Every exception carries the rule ID, rule version, verbatim clause, evidence values and the run manifest.
4. **Unknown is not pass.** Missing or ambiguous data yields "not evaluable" plus a data-quality exception, never a silent pass.
5. **The tool recommends; a person decides.** Every exception needs a human decision. Dismissing a High or Critical exception needs a second person.
6. **Precision is a feature.** A noisy queue is an ignored queue. Rules ship only after backtesting, and a flood guard holds runaway rules.
7. **Explain like a colleague.** Plain language, neutral tone, sentences of 25 words or fewer, the fix on the first screen, in English or Arabic.
8. **Process, not people.** Exceptions describe transactions and controls, not character. No individual risk scores, ever.
9. **Replayable to the byte.** The same inputs, rule pack and configuration produce identical outputs and identical hashes.
10. **Deployable inside the walls.** Runs fully offline in Emirates' environment. AI is optional and local.

# 4. NON-NEGOTIABLES

1. **The engine decides, the model explains.** `packages/engine` has no model, network, clock or randomness imports, enforced by a dependency-cruiser rule.
2. **Census.** Every transaction × every active rule ends in exactly one outcome: PASS, FAIL, NOT_APPLICABLE or NOT_EVALUABLE. Finalize asserts completeness (FS-02).
3. **Determinism.** The same inputs give byte-identical output and the same output hash: canonical JSON (RFC 8785), SHA-256, stable sorting, integer fils, explicit as-of date.
4. **Never invent a fact.** Missing or ambiguous data gives NOT_EVALUABLE with a DQ code. A default can influence an outcome only with a caveat in the evidence.
5. **Every exception is complete:** rule ID and version, verbatim clause, evidence (field, value, requirement, comparison), severity with rationale, owner with routing rationale, corrective action, caveats, and explanations in English and Arabic.
6. **Identity.** Exception key = SHA-256(tenant ‖ transaction row ID ‖ rule ID ‖ clause ID). Upserts are idempotent and each run appends an observation.
7. **Humans reduce scrutiny; the engine never does.** The engine may only create, reopen, or return an expired accepted risk to triage. Dismiss, accept risk, verify and close are human commands.
8. **Conflict-of-interest guard, two-person rule approval, countersign for High and Critical dismissals.** Enforced in the API and in the database, not only in the UI.
9. **Tamper-evident audit.** Append-only, hash-chained events; hourly verification; a failure enters safe halt.
10. **No writes to any source system.** MIZAN never holds write credentials.
11. **Synthetic data only.** PII scanner on uploads; judge mode refuses untagged datasets.
12. **Fact-lock** on any model text, with canonical template fallback.
13. **Free text is data, never instructions.**
14. **Guards:** flood guard, run-level routing hold and not-evaluable spike guard.
15. **Pattern alerts are advisory:** never exported, never routed as breaches, protected attributes excluded.
16. **One retry helper, explicit timeouts on every call, typed errors, no empty `catch`.**
17. **Idempotency keys on every mutating endpoint; transactional outbox and consumer inbox.**
18. **Caches are never authoritative.** The system is correct with Valkey switched off.
19. **WCAG 2.2 AA, and Arabic right-to-left as a first-class layout.**
20. **Every state is designed:** loading, empty, error, partial, held, stale, offline, no access, and every degraded mode.
21. **Exports validate** against `finding_format.csv`, and the 5 worked examples reproduce exactly.
22. **Configuration is versioned data:** routing, calendars, grade ladder, synonyms, severity rubric, service levels and templates.
23. **Small cells below 5 are suppressed** in analytics.
24. **No personal data** in logs, metrics or traces.
25. **Safety controls are code, not flags.**

# 5. STACK

- **Monorepo:** Turborepo with pnpm workspaces. TypeScript 5 with `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`. ESLint (typescript-eslint strict, plus custom rules: no floats on money paths, no raw colours, sizes or durations in UI components, no empty catch, no hand-written retry loops, no `Date.now()` or `Math.random()` in the engine), Prettier, dependency-cruiser.
- **Runtime:** Node.js 22 LTS.
- **Web:** Next.js 15 (App Router) with React 19; TanStack Query, TanStack Table and TanStack Virtual; Radix UI primitives; Tailwind CSS 4 driven by SADU CSS variables; Motion (Framer Motion) with token presets; Lucide icons plus the custom glyph set; next-intl with ICU MessageFormat; visx for charts and the heatmap.
- **API:** Fastify 5 with Zod and `fastify-type-provider-zod`; OpenAPI 3.1 generated from Zod; RFC 9457 problem details.
- **Data:** PostgreSQL 16 (row-level security, partitioning, `SKIP LOCKED`), Kysely with plain SQL migrations, pg-boss queues, transactional outbox and inbox tables.
- **Cache:** Valkey 8, non-authoritative.
- **Object storage:** S3-compatible (MinIO locally) with object lock (WORM) for evidence packs and audit anchors.
- **Model gateway:** adapters `none` (default), `local` (OpenAI-compatible endpoint such as vLLM or Ollama) and `provider` (an approved zero-retention deployment).
- **Identity:** OIDC. Keycloak in Compose for development and judge mode; Microsoft Entra ID or ADFS in production.
- **Observability:** OpenTelemetry SDK to an OTLP collector; Prometheus metrics; Grafana dashboards stored as JSON in the repository.
- **Testing:** Vitest, fast-check, Testcontainers, Playwright with axe-core, k6, plus the backtesting harness in `packages/testkit`.
- **Packaging:** Docker (slim or distroless images), Docker Compose, Helm chart, cosign signatures, Syft CycloneDX SBOM, Trivy scans.

# 8. INGESTION AND NORMALISATION

**Pipeline:** receive (stream to object storage while hashing with SHA-256) → sniff (magic bytes; encoding from BOM, UTF-8 validity, UTF-16 or Windows-1256; delimiter from the first 64 KB) → parse (RFC 4180 streaming parser; limits of 50 MB per file, 1 MB per line, 32 KB per field and 2,000,000 rows) → header mapping (synonym tables, header fingerprint, saved mapping profile) → field normalisation → schema validation → quarantine of invalid rows → dataset record with an issues summary. Identical bytes return the existing dataset.

**Field normalisers** (each a pure function with unit and property tests):
- Text: NFKC, strip zero-width characters, collapse whitespace, trim; flag confusable characters (DQ-014). Missing tokens (empty, whitespace, N/A, null, -) become missing (DQ-001 where required).
- Digits: Arabic-Indic and Persian digits, the Arabic decimal separator (٫) and thousands separator (٬) become ASCII before any parsing.
- Dates: ISO, day-month-year with `/`, `-` or `.`, two-digit years (pivot 2000), month names in English and Arabic, spreadsheet serials (20,000–80,000). Day-month order is inferred per column from unambiguous values; a fully ambiguous column defaults to day-month with DQ-003; cells contradicting the column's order get DQ-002.
- Timestamps: explicit offsets honoured; no offset means Asia/Dubai (UTC+4, no daylight saving); stored as UTC instants with a precision flag.
- Amounts: strip currency words and symbols; decide the decimal convention per column; parentheses mean negative; scientific notation allowed; convert to integer fils. More than 2 decimals or a value ambiguous under the column convention gives DQ-013. Currency other than AED gives DQ-009, and amounts are never converted without a versioned FX table.
- Identifiers: canonicalise with the tenant pattern from configuration (case, prefix, zero padding); log every mapping; a collision onto a different person gives DQ-014.
- Lists: approvers and documents from `;`, `,`, `|`, JSON arrays or numbered columns (`approver_1` … `approver_n`), keeping order and removing exact repeats with a caveat.
- Vocabularies: transaction types, document types, statuses, departments and locations map through versioned synonym tables; unknown values get DQ-006, DQ-007 or DQ-016 and are suggested to a person, never auto-accepted.
- Booleans: Y, yes, true, 1, نعم and their negatives.
- Free text: stored verbatim as quoted data, scanned for instruction-like text (DQ-017) and never read by the engine.

**Mapping review.** Unknown columns, low-confidence header matches and new vocabulary values appear on a mapping screen. Confirmed choices are saved as a versioned mapping profile that is pinned in the run manifest. Every edge case in sections 34.A and 34.B must pass.

# 9. RULE MODEL, DSL AND COMPILER

## Spec · PRD §10 Rule model

Each written rule becomes a RuleSpec, typed, versioned, effective-dated and tested, plus an InterpretationRecord that states how MIZAN reads the sentence and why.

| Family | What it checks | Example | Parameters | Evidence captured |
| --- | --- | --- | --- | --- |
| `approval_limit` | Approver authority against amount | Allowance change above AED 10,000 needs a grade 13+ approver | Threshold, comparator, minimum grade or role, quantifier | Amount, threshold, approver grades, required grade |
| `approval_count` | Number and roles of approvers | Exits need the line manager and an HR business partner | Minimum approvers, distinct, required roles | Approvers, roles found and missing |
| `approval_chain` | Approver sits in the employee's management chain | Transfers need the sending and receiving managers | Chain depth, receiving manager | Chain path, managers |
| `segregation_of_duties` | One person in incompatible roles | Requester cannot approve; nobody approves their own change | Forbidden role pairs | Person IDs per role |
| `required_documents` | Mandatory attachments by type and condition | A hire needs an offer letter, passport copy and visa | Required set, conditions | Attached (normalised), missing |
| `timing_window` | Interval limits between dates | No backdating beyond 30 days; approval before the effective date | From, to, maximum or minimum, calendar basis, inclusivity | Dates, interval, limit, calendar version |
| `sequence` | Order of events | Approval after submission; approvals in order | Ordered facts, strictness | Timestamps |
| `eligibility` | Employee status or tenure at the effective date | No pay change for an exited employee; no transfer during probation | Allowed statuses, probation length | Status, hire and exit dates |
| `aggregate_limit` | Counts or sums across a window | No more than 2 allowance changes per employee in 12 months | Window, metric, maximum, grouping | Contributing transaction IDs, totals |
| `duplicate` | The same change entered twice | Same employee, type and amount within 3 days | Keys, tolerance | Twin transaction IDs |
| `reference_integrity` | Referenced people exist and are active | Approver must be an active employee at approval time | Facts, active-at date | Lookups |
| `value_bounds` | Ranges and percentage caps | A pay increase above 15% needs an extra approval | Fact, minimum, maximum, percentage | Value, bound |

**Lifecycle.** Draft → tested → backtested → approved by two people (author ≠ approver) → shadow (evaluates, does not route) → active → retired. Versions are immutable. A change is a new version with an effective-from date, and every exception pins the rule version that produced it.

**Semantics decided up front.** Each is recorded as an architecture decision record and shown in the product under "How MIZAN reads this rule".

- "Above", "over", "more than" mean strictly greater. "At least", "or above", "and above" mean greater than or equal.
- "Within N days" includes day N. Calendar days unless the rule says business days; business days use the versioned UAE calendar with a Saturday–Sunday weekend and public holidays held as data.
- Grade comparisons use the configured grade ladder (direction and ordinal). A grade not on the ladder makes the check not evaluable.
- The transaction's effective date selects the rule version in force unless the rule says otherwise.
- Delegated approvals count only if the policy allows delegation and the delegate meets the same authority requirement.
- Approver grade comes from the transaction when present, otherwise from the employee master snapshot, and the evidence says which.

    id: R04
    title: Allowance changes above AED 10,000 need a grade 13+ approver
    family: approval_limit
    version: 1.0.0
    status: active
    effective: { from: 2025-01-01, to: null, date_basis: effective_date }
    source: { document: policy_rules.md, anchor: "R04", text: "<verbatim clause>", sha256: "<hash>" }
    scope:
      transaction_types: [ALLOWANCE_CHANGE]
      where: { all: [ { fact: txn.amount_fils, op: gt, value: 1000000 } ] }
    check:
      kind: approval_limit
      params: { min_approver_grade: 13, quantifier: any, allow_delegates: false }
    severity: { base: high, modifiers: [magnitude_over_limit, exposure_50k, repeat_actor_90d] }
    routing: { process: compensation }
    action: { template: CA-AL-01 }
    explain: { template: EX-AL-01 }
    tests:
      - { name: at_threshold_is_out_of_scope, given: { amount: "10000.00", approver_grades: [9] }, expect: not_applicable }
      - { name: one_fils_over_fails, given: { amount: "10000.01", approver_grades: [12] }, expect: fail }
      - { name: required_grade_passes, given: { amount: "15000.00", approver_grades: [13] }, expect: pass }

**Condition grammar** for `scope.where` and conditional parameters: `{ all: [...] }`, `{ any: [...] }`, `{ not: {...} }`, `{ fact, op, value }` with ops `eq, ne, gt, gte, lt, lte, in, nin, between, exists, missing`. No regular expressions and no code in specs. Every `fact` must exist in the fact catalogue (section 7 derived facts), otherwise compilation fails with `MZ-RULE-422`.

**Family semantics** (each family is one module in `packages/engine/families/` with its own tests):
- `approval_limit` { thresholdFils, comparator gt|gte, minApproverGrade, quantifier any|all, allowDelegates }: the amount precondition lives in scope (so an amount at the threshold under "above" is NOT_APPLICABLE). With `any`, PASS if at least one counted approver meets the grade, even if others are unknown; FAIL if all approvers have known grades below it; otherwise NOT_EVALUABLE. With `all`, any unknown grade makes it NOT_EVALUABLE. Exited approvers and system actors are not counted. Evidence states the source of every grade (transaction or master snapshot).
- `approval_count` { minDistinct, requiredRoles[] }: distinct people; roles resolved from the transaction role field, the employee master roles or the management chain (line manager); unresolvable role information gives NOT_EVALUABLE.
- `approval_chain` { mustInclude: line_manager | receiving_manager | within_depth(n) }: management graph from the employee master; cycles give DQ-010 and NOT_EVALUABLE.
- `segregation_of_duties` { forbiddenPairs: [requester, approver] | [beneficiary, approver] | [requester, beneficiary] }: compares canonical person IDs; NOT_EVALUABLE if a needed person field is missing.
- `required_documents` { required[], conditions }: missing set = required − normalised attached set; FAIL lists every missing document; documents column absent or condition fact missing gives NOT_EVALUABLE; unrecognised attachments appear as caveats and never count.
- `timing_window` { fromFact, toFact, maxDays|minDays, basis calendar|business, inclusive }: signed day difference in Asia/Dubai; business days use the versioned calendar; a date outside the calendar gives DQ-015.
- `sequence` { order[], strict }: compares instants, or dates at day precision with a caveat when either side lacks a time.
- `eligibility` { allowedStatuses, exemptTypes, probationDays }: point-in-time status derived from employment spells at the effective date; active through the exit date inclusive.
- `aggregate_limit` { windowDays, metric count|sum, max, groupBy, anchor: effectiveDate }: for each transaction, the window [anchor − windowDays + 1, anchor] in effective-date order (ties broken by submission time, then row ID); a transaction FAILs when the running total including it exceeds the maximum; evidence lists contributing IDs.
- `duplicate` { keys[], toleranceDays, ignoreReversals, flag: later|both }: the default `later` flags the later twin (effective date, then submission time, then row ID) and cites the earlier one; choose `later` or `both` from the worked examples and record an ADR.
- `reference_integrity` { facts[], activeAt: effective|approval }: FAIL when a referenced person does not exist or is inactive at the reference time.
- `value_bounds` { fact, min?, max?, pctOf?, pctMax? }: a percentage needs a known base; an unknown base gives NOT_EVALUABLE unless it can be derived from earlier transactions, which the evidence states.

**Clauses.** A rule with several requirements (a), (b) emits one result per clause, with clause IDs `C1`, `C2` and so on in the order of the text. A family never emits one result per list item (for example, one exception lists all missing documents).

**Precedence and conflicts.** Overlapping scopes with opposite outcomes are detected at compile time; the pack must declare precedence (specific over general), and the interpretation record shows it.

**Compilation.** Specs compile to typed closures (no `eval`, no dynamic code), validated against the fact catalogue. A pack is the sorted set of specs, calendar references, ladders and synonyms; `packHash` = SHA-256 of its canonical JSON.

# 10. RULE PACK FROM policy_rules.md

1. Parse the Markdown into sections. Detect rule anchors (IDs such as R01, "Rule 1" or numbered headings) and store each rule's verbatim text, anchor and SHA-256. Duplicate IDs fail compilation with both anchors shown (EC-I13).
2. Classify every sentence as check, definition (for example the grade ladder), scope note or human attestation. Definitions become configuration and are linked from the rules that use them. Clauses needing human judgement are marked "not automatable: human attestation" and are never claimed as covered.
3. Parse each check with the deterministic grammar first. Use the model only if it is enabled, and then only to propose JSON that must validate against the RuleSpec schema.
4. Write an interpretation record per rule: readings considered, the chosen reading, ambiguity chips (> or ≥, calendar or business days, any or all approvers, monthly or annual amounts), and the evidence for the choice (policy wording, worked examples). Each choice is an ADR.
5. Generate tests for every rule: just below, at and just above every boundary; out of scope; missing data; and the matching worked example if one exists.
6. Reproduce the 5 worked examples in `finding_format.csv` exactly. If a reading conflicts with an example, the example wins and the ADR records it.
7. Produce `docs/RULES.md`, generated from the interpretation records: for each rule, the verbatim text, "How MIZAN reads this rule", parameters, tests and coverage.
8. Coverage report: every sentence in `policy_rules.md` is compiled, definition, scope note or human attestation, with none missing.

# 11. DETECTION ENGINE

## Spec · PRD §11 Detection engine and outcome semantics

- A pure TypeScript package: no I/O, no wall clock, no randomness, integer money, canonical JSON hashing (RFC 8785) and stable sorting.
- Evaluation order per transaction and rule: scope check (not applicable) → data sufficiency (not evaluable) → check (pass or fail) → evidence record.
- All four outcomes are stored, which makes the coverage matrix possible: rows are rules, columns are outcome counts, and every cell drills down to transactions.
- Census proof banner, with every number clickable (illustrative figures): "10,000 transactions × 18 rules = 180,000 checks · 41,220 applicable · 40,964 evaluated · 256 not evaluable · 312 failed".
- **Flood guard.** If a rule's fail rate in a run exceeds the larger of 3× its backtest baseline or baseline + 2 percentage points, its new exceptions are held rather than routed and the rule owner is alerted. The run still completes and the hold is visible.
- **Precision safeguards.** Scope preconditions on every rule, normalisation tests, a near-miss suite and grouping by root cause. One approver self-approving 9 transactions produces 9 exceptions in one group.
- **Performance.** 10,000 × 20 in ≤ 10 seconds end to end on a laptop; 1,000,000 transactions in ≤ 10 minutes across 16 shards.
- **Run manifest.** Engine version, rule pack hash, calendar hash, configuration hash, input file hashes, counts and output hash. Two runs on the same inputs produce the same output hash.

**Signature.** `evaluate(input: { transactions, employeeIndex, pack, calendar, config, asOf, shard? }) → { results: CheckResult[], counts, outputHash }`. It is pure, synchronous per shard and returns `Result` values; it never throws for business outcomes. A failing rule module yields NOT_EVALUABLE with a reason, never an aborted run.

**Algorithm.** Pre-index employees (spells, ladder ordinals, management graph with cycle detection) and per-employee transaction lists sorted by effective date. For each transaction in row-ID order and each rule in rule-ID then clause-ID order: select the rule version by its date basis → scope (NOT_APPLICABLE) → data sufficiency (NOT_EVALUABLE with DQ codes) → check (PASS or FAIL) → evidence → evidence hash. Shard by `hash(employeeId) mod 16` so aggregate and duplicate rules stay within a shard. `outputHash` = SHA-256 over the sorted tuples (rowId, ruleId, clauseId, outcome, evidenceHash).

**Run pipeline.** `POST /runs` (or the CLI) → `run.evaluate.shard` jobs writing to a run-scoped staging partition → `run.finalize` (fencing check, census completeness, determinism sample, flood guard, routing hold, not-evaluable spike guard, idempotent exception upsert, observations, outbox rows, manifest, projection version bump) in one transaction. The as-of date is an explicit input; the CLI default is the day after the latest date in the dataset, recorded in the manifest.

**Export.** Only FAIL results become findings in the official file. NOT_EVALUABLE results go to `data_quality.csv` in the same bundle. The exporter uses the ExportProfile learned from `finding_format.csv` (column order, enumerations, ID and date formats, encoding, line endings), is byte-deterministic, and passes the export validator (FS-20) before the file can be downloaded.

- **Identity.** Exception key = hash(tenant, transaction ID, rule ID, clause ID). Re-running the same data never duplicates an exception; each run adds an observation with the rule version and evidence hash.
- **Grouping.** Exceptions sharing a root cause (actor + rule + 90-day window) are grouped for triage. A group decision is applied by a person to each listed member and recorded per exception. High and Critical dismissals cannot be applied in bulk.

**Fact-lock algorithm** (`packages/explain/factlock.ts`):
1. Build the allowed token set from the evidence: every fact display value; numbers with and without thousands separators, in Western and Arabic-Indic digits; dates in every display format (25 Mar 2026, 2026-03-25, ٢٥ مارس ٢٠٢٦); IDs; the rule ID; the action ID's parameters; the owner team name; severity labels.
2. Tokenise the output for numbers, money, dates and ID-like strings.
3. Reject if any token is not in the allowed set, if the rule ID or the action is missing, if a banned term appears (English: fraud, deliberate, negligent, suspicious; Arabic: احتيال، متعمد، إهمال، مشبوه, matched after removing diacritics and tatweel), if the length exceeds 1.5 times the canonical text or 120 words, or if the script does not match the requested locale.
4. On rejection, show the canonical text and log a reason code: FL-NUM, FL-DATE, FL-ID, FL-RULE, FL-ACTION, FL-BANNED, FL-LENGTH, FL-LOCALE or FL-SCHEMA.
5. The UI labels polished text "Polished by AI · view canonical", and the export always uses canonical text.

## Spec · Platform §3 Request lifecycle

Middleware runs in this order on every request:

1. Assign or accept `X-Request-Id`; start the trace span; attach the correlation ID to the log context.
2. Authenticate (session cookie or service token). Reject with `MZ-AUTH-401`.
3. Enforce the mode: in read-only or safe halt, reject writes with `MZ-MODE-503` and `Retry-After`.
4. Rate-limit by actor and route class. Reject with `MZ-RATE-429` and `Retry-After`.
5. Idempotency check for side-effecting POSTs (section 6).
6. Validate input with the route's Zod schema. Reject with `MZ-VAL-422` and field errors.
7. Authorise: role, row-level scope, and for decisions the conflict-of-interest check.
8. Execute the handler inside a per-route time budget with an `AbortSignal`.
9. Inside the same database transaction: state change, audit event, outbox row.
10. Serialise the response, set `ETag`, cache headers and the request ID; end the span.

## Spec · Platform §9 Concurrency and consistency

- Optimistic concurrency on exceptions and rule drafts through `version` and `If-Match`. No last-writer-wins anywhere.
- Every command writes, in one transaction: the state change, an audit event appended to the hash chain, and an outbox row. Either all three exist or none do.
- Read-your-writes: command responses return the new version and event hash; the client updates from that response, not from a refetch race.
- Monotonic reads for run status: the client discards any status older than the one it holds.
- The audit chain orders events by a database sequence, never by wall-clock time. Each event stores `prev_hash` and `hash = SHA-256(prev_hash ‖ canonical_json(event))`.

## Spec · Platform §10 Queues and jobs

Postgres-backed queues (pg-boss with `FOR UPDATE SKIP LOCKED`) keep the job, the data and the outbox in the same transactional store, which makes exactly-once effects achievable with at-least-once delivery.

- **Sharding.** Evaluation shards by `hash(employee_id) mod 16` so per-employee aggregate and duplicate rules stay inside one shard.
- **Leases and fencing.** A job holds a lease with a heartbeat every 10 s. Losing the lease increments `lease_epoch`; finalize refuses to write with a stale epoch.
- **Poison messages.** After the final attempt a job moves to `dlq.<queue>` with payload, error chain and trace ID. `mizan dlq list | show <id> | replay <id> | replay --all --since <time>` re-enqueues after a fix, and replay is safe because every job is keyed.
- **Outbox relay.** Polls `outbox` with `SKIP LOCKED` in batches of 100, publishes, then marks sent. Consumers dedupe through the inbox table.
- **Backpressure.** At most 2 in-flight runs per tenant. When queue depth implies a wait above 60 s, new run requests get `429` with a computed `Retry-After`, and the UI shows "Queued: 2 runs ahead, about 40 s".
- **Load-shedding order.** Narrative polish → pattern detection → analytics refresh (dashboards labelled stale) → backtests and archive → evidence packs deferred with an ETA. **Never shed:** ingestion, evaluation, finalize, decisions, audit writes, deadline ticks, integrity verification.

## Spec · Platform §11 Retries and exponential backoff

One shared helper, used everywhere. Full jitter: `delay = random(0, min(cap, base × 2^(attempt − 1)))`, raised to `Retry-After` when the server provides it, and never beyond the overall deadline.

| Dependency | Base | Cap | Max attempts | Overall deadline | Retry on | Never retry on |
| --- | --- | --- | --- | --- | --- | --- |
| Postgres (whole transaction) | 50 ms | 1 s | 5 | 3 s interactive, 60 s batch | Serialisation failure 40001, deadlock 40P01, connection reset | Constraint violations, syntax, permission |
| Object store | 200 ms | 5 s | 5 | 30 s | Timeouts, 429, 500, 502, 503, 504, connection reset | 400, 403, 404 on a content-addressed key |
| LLM gateway | 500 ms | 8 s | 3 interactive, 4 queued | 8 s / 15 s | Timeouts, 429, 5xx | Schema-invalid output (fall back instead), 400 |
| Notifications | 5 s | 15 min | 8, then dead-letter | 2 h | Timeouts, 429, 5xx | 4xx except 408 and 429 |
| Browser → API (GET only) | 300 ms | 5 s | 3 | 10 s | Network error, 502, 503, 504, `MZ-RATE-429` | Any 4xx; POST without an idempotency key |

**Retry budget.** Each dependency has a token bucket: every first-attempt call adds 0.1 tokens (maximum 10) and every retry spends 1. Retries therefore stay under 10% of traffic, and a failing dependency gets fast failures instead of a retry storm.

    // packages/reliability/src/retry.ts — the only retry implementation in the repo.
    export interface RetryPolicy {
      name: 'postgres' | 'objectStore' | 'llm' | 'notify' | 'http';
      baseMs: number;
      capMs: number;
      maxAttempts: number;   // includes the first attempt
      deadlineMs: number;    // across all attempts
      retryOn: (e: unknown) => boolean;
    }

    export async function withRetry<T>(
      policy: RetryPolicy,
      op: (attempt: number, signal: AbortSignal) => Promise<T>,
      ctx: RetryContext, // { signal, budget, rng, now, sleep, log } injected for determinism in tests
    ): Promise<T> {
      const startedAt = ctx.now();
      let last: unknown;
      for (let attempt = 1; attempt <= policy.maxAttempts; attempt++) {
        const remaining = policy.deadlineMs - (ctx.now() - startedAt);
        if (remaining <= 0) break;
        const controller = new AbortController();
        const timer = setTimeout(() => controller.abort(new DeadlineExceeded(policy.name)), remaining);
        const relay = () => controller.abort(ctx.signal?.reason);
        ctx.signal?.addEventListener('abort', relay, { once: true });
        try {
          const result = await op(attempt, controller.signal);
          if (attempt === 1) ctx.budget.deposit(policy.name);
          return result;
        } catch (error) {
          last = error;
          const canRetry = policy.retryOn(error) && attempt < policy.maxAttempts && ctx.budget.withdraw(policy.name);
          ctx.log.warn({ dependency: policy.name, attempt, retrying: canRetry, code: errorCode(error) });
          if (!canRetry) throw new DependencyError(policy.name, attempt, { cause: error });
          const ceiling = Math.min(policy.capMs, policy.baseMs * 2 ** (attempt - 1));
          const jittered = Math.floor(ctx.rng() * ceiling);
          const delay = Math.max(jittered, retryAfterMs(error) ?? 0);
          const left = policy.deadlineMs - (ctx.now() - startedAt);
          await ctx.sleep(Math.min(delay, Math.max(0, left)), ctx.signal);
        } finally {
          clearTimeout(timer);
          ctx.signal?.removeEventListener('abort', relay);
        }
      }
      throw new DependencyError(policy.name, policy.maxAttempts, { cause: last });
    }

## Spec · Platform §12 Circuit breakers, bulkheads and timeouts

- **Circuit breakers** on the LLM gateway, object store, notification channel and Valkey. Closed → open when ≥ 50% of at least 20 calls fail within 30 s, or after 5 consecutive timeouts. Open for 30 s, then half-open with 3 probes; success closes it, failure reopens it with the open period doubling up to 5 minutes. Breaker state is a metric and drives the mode banner.
- **Bulkheads.** Separate connection pools: interactive role (20 connections, `statement_timeout` 3 s) and batch role (10 connections, 120 s). Separate worker pools for warm and cold queues, so a backtest never starves a decision.
- **Timeouts, all explicit.**

| Call | Timeout |
| --- | --- |
| Browser fetch | 10 s reads, 15 s writes |
| API handler budget | 2 s interactive, 30 s upload acknowledgement |
| Postgres statement | 3 s interactive, 120 s batch; idle in transaction 10 s |
| LLM | 8 s interactive, 15 s queued |
| Object store | 5 s per operation, 30 s per multipart part |
| Notifications | 5 s connect, 10 s total |
| Job lease | Equal to the job timeout, with 10 s heartbeats |

## Spec · Platform §13 Error handling discipline

- Typed errors only: `ValidationError`, `AuthError`, `ConflictError`, `DependencyError`, `DeadlineExceeded`, `InvariantViolation`, each carrying an `MZ-` code, `retryable` flag and `cause`.
- The engine never throws for business outcomes. It returns `Result<Outcome, EngineError>`; a failing rule becomes `NOT_EVALUABLE` with a reason, never an exception that aborts the run.
- **No bare catch.** Every `catch` does one of three things: handle with a typed fallback, translate and rethrow with `cause`, or record and rethrow. Swallowing an error is a lint failure.
- `finally` releases resources: timers, listeners, locks, file handles, leases.
- `InvariantViolation` (for example, an audit hash mismatch or an evidence hash that does not reproduce) opens an integrity incident and moves the system to safe halt. It is never retried.
- Unhandled rejections and uncaught exceptions crash the process after flushing telemetry; the orchestrator restarts it. Silent zombie processes are worse than restarts.
- HTTP mapping is centralised in one error handler that emits problem details and never leaks stack traces or SQL.

    try {

      if (error instanceof DependencyError || error instanceof FactLockRejected) {

            │ workers     │                     │ workers     │   both pull from the same queue
            │ Valkey (A)  │                     │ Valkey (B)  │   caches: per site, disposable
            │ PG primary ─┼──── synchronous ────┼─► PG standby│   one writer at a time
            └─────────────┘                     └─────────────┘

            Object store: replicated across sites, content-addressed, immutable

- **What is active-active.** Web, API and workers run in both sites and serve traffic at the same time. Workers in both sites claim jobs from the same Postgres queue; `SKIP LOCKED` distributes work without coordination.
- **What is single-writer.** Postgres has one primary at a time with a synchronous standby in the other site (Patroni or a managed high-availability service) and a witness for quorum. This is a deliberate choice: audit trails and human decisions must have one order.
- **Why duplicate work is harmless.** The engine is deterministic and every write is an idempotent upsert keyed by content, so a job that runs in both sites during a failover produces identical rows. Fencing tokens stop a worker that lost its lease from writing.
- **Split-brain prevention.** Only the elected leader accepts writes. The application checks `pg_is_in_recovery() = false` on connection checkout for the write pool.
- **Idempotency keys** live in Postgres, so they survive failover; Valkey is only a fast path.
- **Clocks.** NTP everywhere; ordering by database sequence; timestamps are informational.
- **Targets.** RPO 0 for Postgres (synchronous commit); RTO ≤ 5 minutes for API and workers; object store replication lag ≤ 15 minutes; point-in-time recovery for 35 days; monthly restore drill into a clean environment.
- **Failover drill (demo-able).** Kill the Site A primary mid-run. Writes pause briefly with `MZ-MODE-503` and `Retry-After: 5`, Site B is promoted, the run resumes from its checkpoint, and the output hash matches the control run.

# 25. OPERATING MODES, FLAGS AND FAILSAFES

## Spec · Edge cases §1 Failure philosophy

1. **Fail closed on integrity, fail open on convenience.** If correctness is in doubt, stop writing. If a convenience breaks (the model, the cache, a chart), drop it and keep going.
2. **Every check ends somewhere.** Each transaction × rule pair ends as PASS, FAIL, NOT_APPLICABLE or NOT_EVALUABLE. A run publishes completely or not at all.
3. **Never invent a fact.** Missing or ambiguous data produces NOT_EVALUABLE with a data-quality code. A default may influence an outcome only when the evidence carries a caveat that states it.
4. **Hold routing before holding detection.** Suspicious volumes pause notifications, not evaluation.
5. **Every mode is visible.** A mode chip in the top bar, a banner in plain language, `GET /api/v1/system/mode`, the metric `mizan_mode` and an audit event on every transition.
6. **People clear the serious modes.** Safe halt clears only when an administrator gives a reason, verification passes and a second administrator countersigns.
7. **Shed in a fixed order.** Narrative polish, then pattern detection, analytics refresh, backtests and archive, and finally evidence packs, which are deferred rather than dropped. Ingestion, evaluation, finalize, decisions, audit writes, deadline ticks and integrity verification are never shed.
8. **Safety controls are code, not configuration.** Flags can restrict behaviour. No flag can relax a safety control.

## Spec · Edge cases §3 Mode controller

- A controller loop in each API region evaluates health signals every 10 s. It writes the current mode to `system_mode` in Postgres, the source of truth, with one row per tenant and region holding the version, reason, signals and start time. It publishes `mode.changed` through the outbox and writes an audit event.
- **Hysteresis.** A mode is entered after 3 consecutive bad readings (30 s) and exited after 6 consecutive good readings (60 s), with a minimum dwell of 2 minutes. M5 is entered on the first failure and M4 immediately on failover.
- **Reading the mode.** Services subscribe through Valkey pub/sub and poll Postgres every 5 s as a fallback. A service that cannot read the mode for 15 s behaves as M4 for writes (fail closed) and keeps serving reads.
- **Operator overrides.** `mizan mode set read-only --reason "…" --ttl 30m`. Every override needs a reason and a time-to-live of at most 24 hours. It appears in the audit trail, and the banner says it was set by an administrator.
- **Entering M5 never deletes or rewrites data.** It records a pointer to the first failing chain segment.

| Audit trail edited after the fact | Append-only, hash-chained events; hourly verification; safe halt on mismatch |
| Prompt injection through CSV free-text | Free text treated as data, never instructions; the model has no tools and cannot change state |
| CSV formula injection in exports | Cells beginning with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with an apostrophe |
| Oversized or hostile uploads | 50 MB limit, type sniffing, streaming parser, row and column caps, quarantine of bad rows |
| Data exfiltration via export | Role-gated exports with purpose field, watermark, rate limit and audit event |
| Privilege escalation | Server-side authorisation, Postgres row-level security, deny by default |

Further controls: single sign-on through OIDC in production; TLS 1.2 or higher in transit; encryption at rest; secrets in a vault; no personal data in logs, traces or metric labels; configurable retention per record type; evidence packs written to immutable storage.

## Spec · Platform §19 Security at the API layer

- Web sessions: `HttpOnly`, `Secure`, `SameSite=Lax` cookies; state-changing requests also require a custom CSRF header. Service accounts use short-lived tokens.
- Authorisation in a single policy function per route, backed by Postgres row-level security with `app.tenant_id`, `app.user_id` and `app.roles` set per transaction. Deny by default.
- Content Security Policy with nonces, no inline scripts, `frame-ancestors 'none'`; HSTS; `X-Content-Type-Options: nosniff`; strict referrer policy.
- Uploads: CSV and Markdown only, type sniffing, 50 MB, row and column caps, streaming parse, no archives.
- Exports: formula-injection neutralisation, watermark with user and time, purpose field, rate limit and audit event.
- Secrets from the environment's vault; dependency and container scanning in CI; CycloneDX SBOM per image; images signed.

Also: OIDC groups map to roles; sessions expire after 8 hours idle; administrator role grants need a second administrator; exports carry a watermark (user and time) and a purpose field; tenant purge removes data from Postgres, object storage and caches; `docs/SECURITY.md` holds the threat model and a control mapping (Dubai Electronic Security Center regulation, UAE Information Assurance standards, ISO/IEC 27001).

# 27. RESPONSIBLE AI

## Spec · PRD §17 Responsible AI

| Use | Where | Data the model sees | Guard | Fallback |
| --- | --- | --- | --- | --- |
| Rule drafting | Rule studio | The author's sentence and the fact catalogue, no transactions | Schema validation, template back-rendering, tests, backtest, two-person approval | Guided builder |
| Narrative polish | Exception detail | One exception's evidence record with pseudonymous IDs | Fact-lock, banned terms, length limits | Canonical template |
| Pattern alerts | Patterns page | None; deterministic statistics | Protected attributes excluded; human review | Not applicable |

- **Human decision on every exception**, with a countersign for High and Critical dismissals. A model cannot change state.
- **Transparency.** Every exception shows the rule, clause, evidence and how the rule is read. The product says when text was polished by a model.
- **Contestability.** Owners can dispute an exception with a reason; disputes feed rule review.
- **Data minimisation.** Models never receive datasets, only one evidence record or one sentence at a time.
- **Fairness.** Disparity monitoring across departments and locations; patterns exclude protected attributes; small cells suppressed.
- **Default deployment.** AI off, or a local model inside the environment. Nothing is sent to services that keep or train on data.
- **Limitations stated.** Rule interpretation can be wrong, snapshot master data can lag reality, and patterns indicate risk, not wrongdoing.

**Responsible-AI statement (for the solution note).** MIZAN decides whether a transaction is an exception using deterministic, versioned rules that people wrote, tested and approved; AI never makes, changes or closes that decision. AI is optional and used in two places only: drafting a rule from plain English, which a person reviews, tests against history and a second person approves; and phrasing explanations, which are checked against the underlying evidence before display and fall back to a fixed template if any detail does not match. Every exception carries its rule, rule version, the exact data behind it and a named owner, and every exception is decided by a person. Nothing is changed in any HR system. All actions are recorded in a tamper-evident audit trail. The prototype processes only the synthetic pack, locally, and sends nothing to services that retain or train on data. Pattern alerts exclude protected characteristics and are reviewed by a person before reaching anyone else.

## Spec · PRD §16.4 Employee experience and fairness principles

1. **Transactions, not people.** Exceptions describe a process gap. Copy never implies intent.
2. **Good faith by default.** Most exceptions are process errors and the language treats them that way.
3. **No surprises.** If a correction will change an employee's pay, record or leave, the owner informs the employee before the change, using a bilingual template that explains what happened, what changes and when.
4. **Right to respond.** The employee can add context through HR, and it is attached to the exception and the trail.
5. **Proportionate response.** Low and Medium exceptions are coaching and process fixes. Any people-related consequence follows existing HR procedures, outside MIZAN.
6. **Fix harm first.** Employee-impacting exceptions such as underpayment are prioritised to be fixed before the next payroll.
7. **Consistency.** The same rule applies to everyone. Exception rates by department and location are monitored for unexplained disparity.
8. **Privacy.** People see the minimum necessary data. Team dashboards suppress small cells.
9. **Human decision.** No exception affects anyone until a person decides.
10. **Bilingual by default.** Employees are addressed in their preferred language.

## Spec · Platform §17 LLM gateway behaviour

- Adapters: `none` (default for judging), `local` (OpenAI-compatible endpoint such as vLLM or Ollama inside the environment) and `provider` (an approved deployment contractually barred from retaining or training on inputs).
- Model pinned by ID and digest; prompts versioned and hashed; temperature 0; JSON-schema-constrained output for rule drafting; token limits per call.
- Inputs: one evidence record with pseudonymous IDs, or one policy sentence plus the fact catalogue. Never a dataset, never names.
- Untrusted content (CSV free text, policy sentences) is wrapped in delimiters and labelled as data. The model has no tools and cannot change state.
- Outputs pass schema validation and, for narratives, the fact-lock. Any failure falls back to the canonical template.
- Logs store prompt and output hashes, model ID and latency, not prompt content.
- Per-tenant rate and cost caps; a kill switch moves the system to degraded AI mode instantly.

Publish the responsible-AI statement above verbatim in `docs/RAI_STATEMENT.md`, in the solution note and on an in-product page "How MIZAN uses AI".

# 33. TESTING AND BACKTESTING

## Spec · Backtesting §1 What accuracy means here

- Judges count planted violations we find and false positives we raise. Each false positive also costs credibility in the explanation and routing score, because every flag must be defended.
- **Precision first, then recall.** A rule only fires when its scope, data sufficiency and check all hold. Ambiguous data becomes "not evaluable" with a data-quality exception, which is not exported as a policy finding unless the worked examples show that category.
- **Unit of scoring:** one row per transaction and rule pair, unless the five worked examples in `finding_format.csv` show a different grain. The export adapter follows the examples exactly.
- **Traps to expect in planted data:** values exactly at thresholds, intervals exactly at window limits, allowed delegations, document synonyms and odd casing, weekends and holidays, approvers promoted or exited around the approval date, duplicate IDs, and transactions that break two rules at once.

## Spec · Backtesting §2 Sources of truth without an answer key

| Source | What it is | What it catches |
| --- | --- | --- |
| Golden examples | The 5 worked examples from `finding_format.csv`, reproduced exactly | Format, grain, ID and wording conventions |
| Interpretation records | For each rule: verbatim text, reading, ambiguities, decision, boundary cases; reviewed by a second person | Misreading the policy |
| Mutation labels | Seeded injections of known violations, each with a near-miss twin that must not fire | Recall gaps and false positives at boundaries |
| Independent oracle | Every rule re-implemented in SQL on DuckDB by a different author from the rule text, with its own parsing | Engine and normalisation bugs |
| Metamorphic invariants | Transformations that must leave results unchanged, or change them predictably | Hidden dependence on order, format or IDs |
| Hand-labelled sample | Stratified sample of engine findings labelled by two reviewers | Real-world precision with a confidence interval |

## Spec · Backtesting §3 Harness

    mizan bench golden                         # reproduce the 5 worked examples, column by column
    mizan bench mutate --seed 42 --per-rule 50 # write mutated datasets + labels.jsonl (positives and near-miss twins)
    mizan bench format --seed 42               # label-preserving format mutations
    mizan bench score --labels labels.jsonl --findings out/findings.csv
    mizan bench oracle                         # DuckDB SQL oracle vs engine, full dataset and all mutated sets
    mizan bench metamorphic                    # run MR-1 … MR-7
    mizan bench determinism --runs 2           # byte-identical output across runs and machines
    mizan bench shift --train data/transactions.csv --test data/transactions_test.csv
    mizan bench perf --scale 10k,100k,1m
    mizan bench report                         # writes reports/<date>/backtest.md and backtest.json

All randomness is seeded and recorded in the report. Mutated datasets are written to `fixtures/mutations/<seed>/` with the manifest of every operator applied.

## Spec · Backtesting §4 Mutation operators

Each operator creates a labelled positive (expected **FAIL** for that rule and no other new failures) and a near-miss twin (expected **PASS** or **NOT APPLICABLE**). Operators are applied to transactions that pass every rule beforehand, so labels are unambiguous.

| --- | --- | --- | --- |

| M-AL-2 | Approval limit | Remove the only approver with the required grade | Required-grade approver present as second of three approvers under an "any approver" rule |
| M-AC-1 | Approval count | Remove one required role | The role supplied by a delegate that the policy allows |
| M-CH-1 | Approval chain | Replace the approver with a same-grade person outside the employee's chain | Replace with the skip-level manager, who is in the chain |
| M-SOD-1 | Segregation of duties | Approver set to the requester | Approver set to the requester's manager |
| M-SOD-2 | Segregation of duties | Approver set to the employee the transaction benefits | Employee as requester on a self-service leave request the policy allows |
| M-DOC-1 | Required documents | Remove one required document | Rename it to a known synonym with different case and extension |

## Spec · Backtesting §6 Metamorphic relations

- **MR-1** Row permutation leaves output bytes unchanged after canonical sorting.
- **MR-2** A consistent relabelling of employee IDs leaves output unchanged apart from the relabelling.
- **MR-3** Adding transactions for a new, unrelated employee leaves existing findings unchanged.
- **MR-4** Scaling every amount below the smallest threshold removes every approval-limit finding and nothing else.
- **MR-5** Shifting all dates by whole weeks on a holiday-free calendar leaves output unchanged.
- **MR-6** Removing one rule from the pack leaves every other rule's findings unchanged.
- **MR-7** Uploading the same file twice creates one dataset and no new exceptions.

## Spec · Backtesting §7 Property-based tests

Using fast-check generators for valid transactions per family:

- Raising an amount never turns an approval-limit FAIL into PASS.
- Raising an approver's grade never turns PASS into FAIL.
- Adding a required document never turns PASS into FAIL.
- Adding an independent approver never creates a segregation-of-duties failure.
- Every evaluation returns exactly one of the four outcomes.
- The evidence record contains every fact the check read.
- Evaluating twice gives identical outcome and evidence hashes.

## Spec · Backtesting §8 Independent oracle

1. A different author (or a separate agent session with no access to engine code) implements each rule in SQL over DuckDB from the RuleSpec text and interpretation record only.
2. The oracle reads the raw CSV with its own explicit parsing rules. It shares only the documented mapping tables (header synonyms, document synonyms, grade ladder, calendar).
3. `mizan bench oracle` compares the sets of failing (transaction, rule) pairs on the training data and every mutated dataset.
4. Any disagreement is triaged: re-read the rule, decide the correct reading, fix the wrong side, add a regression case, and update the interpretation record if the reading was clarified.
5. Gate: zero disagreements.

## Spec · Backtesting §9 Metrics

    precision  = TP / (TP + FP)
    recall     = TP / (TP + FN)
    F1         = 2PR / (P + R)
    F0.5       = 1.25PR / (0.25P + R)            # precision-weighted; reported alongside F1
    FP_per_1k  = 1000 × FP / transactions
    NE_rate    = not_evaluable / applicable_checks
    coverage   = evaluated_checks / applicable_checks

    Wilson 95% interval for precision from a hand-labelled sample of n findings, p = share correct, z = 1.96:
    centre     = (p + z²/(2n)) / (1 + z²/n)
    half_width = z × sqrt(p(1 − p)/n + z²/(4n²)) / (1 + z²/n)

| Gate | Threshold | Effect |

| Not-evaluable rate | ≤ 1% of applicable checks on training data | Warning; investigate |
| Hand-labelled precision | Lower bound of the Wilson interval ≥ 0.90 | Blocks submission |

## Spec · Backtesting §11 Explanation and routing evaluation

**Automated, on every finding**

- Completeness: headline, what broke, rule ID, version and verbatim clause, at least one evidence item with value and requirement, action, owner, severity rationale.
- Consistency: every number, date and ID in the canonical text appears in the evidence (the fact-lock runs on templates too, which catches template bugs).
- Readability: English reading grade ≤ 9 and sentences ≤ 25 words; Arabic sentences ≤ 30 words.
- Banned terms absent; no unresolved placeholders, `undefined` or `NaN`.
- Bilingual parity: the English and Arabic versions contain the same numbers, IDs and dates.

**Human rubric, 40 findings stratified by rule, two reviewers including a native Arabic speaker**

| Criterion | Scale | Target |
| --- | --- | --- |
| Clear: what broke is understood in under 15 seconds | Yes / no | ≥ 95% yes |
| Correct: matches the data | Yes / no | 100% yes |
| Cited: the right rule and clause | Yes / no | 100% yes |
| Actionable: the next step is obvious and feasible | 1–5 | Mean ≥ 4 |
| Fair: neutral and non-blaming | Yes / no | 100% yes |
| Routed sensibly | Yes / no | ≥ 95% yes |
| Severity sensible | Yes / no | ≥ 90% yes |

Agreement between reviewers is reported as Cohen's kappa; below 0.6 the rubric wording is tightened and the round repeated.

## Spec · Backtesting §12 Pattern alert validation

- Inject 10 instances of each pattern (P01–P10) into a clean copy across 5 seeds.
- Every injected instance must rank in its detector's top 20; precision at 20 is reported.
- Stability: Jaccard similarity of the top 20 across seeds ≥ 0.8.
- Fairness: a static check proves no protected attribute is in any feature; alert rates by department are reported, and any department above 3× the median without matching rule exceptions is reviewed.
- Pattern alerts never appear in the exported findings file; a test asserts it.

## Spec · Backtesting §15 Distribution shift checks

| Check | Threshold | Action |
| --- | --- | --- |
| Column set and types | Any difference | Explicit mapping with ADR |
| Nulls per column | > 2× training rate | Inspect; not-evaluable where required |
| New transaction types, documents, departments, locations, grades | Any | Synonym or ladder entry with ADR; never a silent default |
| Date range and currency codes | Outside training range or not AED | Confirm calendar coverage and currency handling |
| Fire rate per rule | Above 3× or below one-third of training, with n ≥ 10; or zero where training had ≥ 10 | Investigate before submission |
| Not-evaluable rate per rule | > 1% | Investigate |
| Data-quality code counts | > 3× training | Investigate |
| Duplicate ID rate | Any increase | Investigate |

## Spec · Backtesting §16 Performance and resilience tests

- Scale generator preserving training distributions (10,000 → 100,000 → 1,000,000), seeded.
- Measured: parse rows per second, checks per second, finalize writes per second, peak memory, end-to-end time; targets in the platform document.
- Hot-path load (k6): 50 concurrent analysts browsing the queue, opening detail and recording decisions; p95 targets must hold.
- Soak: 2 hours with periodic runs; memory growth ≤ 10%.
- Chaos: kill a worker mid-shard, kill the database primary, stop Valkey, inject model timeouts. Pass criteria: identical output hash, no duplicate exceptions, no lost decisions.

## Spec · Backtesting §17 Regression corpus

- `fixtures/regression/<id>/` holds `input.csv`, `expected.jsonl` and a `README.md` describing the bug.
- Every defect fix adds a case. Cases are never deleted.
- Golden updates need a reviewer and a reason in the commit message.

## Spec · Edge cases §9 Runbooks

Each runbook follows the same five steps: detect, contain, recover, verify and communicate.

**RB-01 · Model gateway outage**
- Detect: breaker-open alert; `mizan_mode{mode="degraded_ai"}`.
- Contain: M1 is automatic; confirm that no narrative jobs are queued.
- Recover: check the provider's status; switch to `ai.mode=local` if available, otherwise wait while the breaker half-opens every 30 s.
- Verify: 3 probes succeed and the fact-lock pass rate on the probe set is at least 99%.
- Communicate: the banner is automatic; post in the pilot channel if the outage lasts more than 30 minutes.

**RB-02 · Flood guard hold**
- Detect: "R07 held" alert to the rule owner.
- Contain: the hold is automatic, and routing pauses for R07 only.
- Recover: inspect a sample of 20 held exceptions. If the cause is a format break, fix the mapping and re-run. If the spike is real, a compliance lead releases the hold with a reason.
- Verify: the re-run fail rate is back within band, or the release is recorded.
- Communicate: tell the owner teams "R07 exceptions are delayed for review".

**RB-03 · Integrity failure (safe halt)**
- Detect: `integrity.verify` fails and the system enters M5.
- Contain: automatic; freeze administrator role changes and snapshot the database.
- Recover: find the first failing segment and compare it with the immutable object-store copy of the chain. If it was tampered with, restore from the immutable copy and open a security incident.
- Verify: full chain verification passes and one verification run reproduces the last run's output hash.
- Communicate: tell the compliance lead and audit within 1 hour, and record the incident.

**RB-04 · Database failover**
- Detect: primary health check fails and the witness decides.
- Contain: M4; the fencing epoch advances.
- Recover: promote the standby, rebuild a new standby and check replication.
- Verify: write probe succeeds, outbox lag is under 60 s and the idempotency log shows no duplicate decisions.
- Communicate: the banner is automatic; write a post-incident note if it lasted more than 5 minutes.

**RB-05 · Hidden test file surprise (T−72h)**
- Detect: schema fingerprint mismatch, DQ spike, flood guard or not-evaluable spike on the hidden file.
- Contain: freeze the rule pack (O5). Never edit rules to fit the file.
- Recover: fix only mapping and normalisation code, with tests. Every change adds a regression case and reruns the full backtest. Never hand-edit outputs.
- Verify: every gate in the backtesting document passes, determinism is 2 of 2 and the export validator passes.
- Communicate: list every change in the submission notes.

**RB-06 · Dead-letter growth**
- Detect: any message in a non-sheddable DLQ.
- Contain: identify the error class with `mizan dlq list`.
- Recover: fix, deploy, then `mizan dlq replay --all --since <time>`.
- Verify: the DLQ is empty and the replay created no duplicates.
- Communicate: write an incident note if users noticed.

**RB-07 · Notification outage**
- Detect: outbox lag above 5 minutes or channel errors.
- Contain: turn the channel flag off if messages are bouncing; in-app continues.
- Recover: restore the channel; the relay drains the backlog as digests.
- Verify: outbox lag is under 60 s.
- Communicate: administrator banner; tell owners to work from the in-app queue.

**RB-08 · Demo-day failure**
- Detect: anything going wrong on stage.
- Contain: switch to the offline laptop profile. If the laptop fails, play the recorded walkthrough from the same point.
- Recover: Reset, then resume the script from the last checkpoint.
- Communicate: say what happened in one sentence and show the mode banner. The degraded modes are part of the story.
